# Changelog

Notable changes to Kavach. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Kavach is pre-alpha: there are no releases yet, and anything may change before v0.1.

## [Unreleased]

### Fixed

- **A payment that arrives out of order with its default stops contact either way round (B2, ADR-012 addendum).** A revocation was scoped by `nbf`, the time Kavach processed the default, so a payment that occurred after a default but arrived after it was processed did not stop it, and a default that arrived after its payment issued a live mandate. Now: a revocation reaches every root whose source time (the issuing event's `occurred_at`, kept in `mandates.source_occurred_at`, migration 022) is at or before the payment's, with a 30 s skew margin; a recorded payment closes the record to earlier events (a barrier, checked atomically with the insert), clamped to receipt + 5 minutes so a source clock that runs ahead cannot hold it closed; a dispute holds the record against new mandates (no release path yet). A payment dated ahead is accepted, not refused. Attack catalog 8 (35 attacks): `future-revocation` removed, `replayed-revocation` orders its events apart. Existing mandate rows keep `nbf`. An issuing event may be dated at most 60 s ahead (T1; 300 s into the past as before).
- **A revocation's audit entry is never lost to a failed write (S3, ADR-012 addendum).** The entry was written after the commit and only logged on failure, so a crash or an unavailable admin store left the audit log short and nothing repaired it. It is now derived from the stored revocation and written once per event (`admin_audit_log.idempotency_key`, migration 021), by the request or by a reconciler that pages through the stored rows. The entry carries `clock_synced` as stored (S4).
- **Authority is issued only on a synchronised clock (S4, ADR-012 addendum).** Making a mandate from an event, and delegating one, now fail closed (503, `Unavailable`) when the clock is not synchronised within 500 ms, the bar the gateway already held a decision to; the mandate service ignored sync status before. Nothing is spent, so the event is retried when the clock recovers. A revocation still applies on any clock, without evaluating the future bound against that clock (a clock that is behind would otherwise refuse a genuine payment as future-dated), and is flagged: `mandate_revocations.clock_synced` (migration 020, nullable), the audit entry and a warning log. New metric `kavach_sor_events_unavailable_total{kind}` and alert `KavachSorEventsUnavailable`; one clock-error bar (`DEFAULT_MAX_CLOCK_ERROR_MS`) for the data plane and the mandate service.
- **A revoking event is applied in one step (B3, ADR-012 addendum).** Revoking and recording the revocation were separate operations, one transaction per root, and the replay guard was spent first. A crash or an unavailable database part-way left some mandates live, and the retry was refused as a replay. The store's new `apply_revocation` revokes every root and its delegations and writes the revocation row in one transaction, under the tenant's mandate lock; a revoking event no longer consumes the time-limited replay guard (its single use is the stored revocation); a failed attempt changes nothing and its retry completes. A new store method, so an adapter outside this repository must implement it (the contract is in `mandate_store::conformance`).
- **A payment (or dispute) event that reaches Kavach late still stops contact (B1, ADR-012 addendum).** Revoking events had the same 300 s freshness window as issuing events, so a `loan.paid` delivered ten minutes late was refused, nothing retried it, and contact continued. A revoking event now has no maximum age; an event from the future, and an old *issuing* event, are still refused. It is scoped by its own `occurred_at` (it never reaches a mandate issued after it) and its single use is the permanent stored revocation, which is now looked up before the (24 h) replay guard, so a repeat after a day revokes nothing. Attack catalog version 7: `stale-revocation` is replaced by `late-revocation` (accepted, revokes nothing newer); the independent verifier and the specification say the same. Still open: B2 (a payment before the default it follows) and B3 (a crash between revoking and recording).

### Changed

- **Breaking (configuration): each system-of-record issuer key is registered for one tenant and one system (ADR-014 §2.1).** `sor_issuers` entries need `tenant_id` (a file without it does not load). An event is accepted only from a key registered for its own tenant and system; one tenant's key can no longer sign for another on a shared stack. An unknown key id, another tenant's key and a bad signature are refused with the same message (`the event is not accepted from this issuer`), and the detail goes to the redacted log only. Startup refuses a key id used twice and the same public key under two ids or two tenants. Existing projects: add `tenant_id` to each issuer, or run `kavach init --force` (a development project needs the new second issuer key for the `issuer-for-another-tenant` attack; without it the attack is inconclusive, never a pass).
- **Attack catalog version 6 (36 attacks):** `issuer-for-another-tenant` (an event signed by another tenant's registered key, judged on the attack mandate and the evidence chain). The mandate vector gains `tenant_id` on its issuers and a `binding_refused` list, verified by `conformance/kavach_verify.py`.

### Added

- **Kill-switch attacks and simulation (K1-3b, ADR-013 §5).** Attack catalog version 5 (35 attacks): `quarantined-agent-acts`, `restricted-agent-contacts`, `reinstate-without-approval`, `self-approved-reinstate`, `certificate-principal-approves`. Each stops the holder agent, attacks the stop, and brings the agent back through the real approval path; judged on the reply and on ground truth (the state read back, nothing minted). `kavach simulate` gains `agent.restrict | quarantine | revoke | reinstate` events, an oracle model of agent state that shares no code with Kavach's, a reconciliation of each change against the evidence's signed records, and the built-in scenario `rogue-agent-quarantined`. The property row *A stopped agent does nothing…* is **Enforced**: the attacks ran on memory and on Postgres in CI. **Projects made before this release need `kavach init --force`:** the kill-switch attacks and reinstatement scenarios need the approver token it writes (`approver.jwt`; the development operator token now also holds the approver role, so that only the distinct-identity rule refuses its own approval); without it they are inconclusive (exit 2), never a pass.

- **Public specifications, `docs/specs/`** (evidence bundle format 2, credential format, mandate and system-of-record event) and an **independent verifier**, `conformance/kavach_verify.py`: Python, standard library only, written from the specification text alone. It verifies the published bundle, checkpoint, JCS, credential, mandate and event vectors and refuses unknown record kinds; CI runs it as the job "Independent verifier".

### Added

- **Agent risk state is enforced (K1-1, ADR-013).** An agent is `active`, `restricted` (reads within its mandate, nothing with an external effect), `quarantined` or `revoked` (nothing). The state is read from the database at every authorization, together with the state of every holder in the mandate's delegation chain, so a mandate delegated from a stopped agent authorises nothing while its parent's holder is stopped; a quarantine suspends mandates without changing them. A state that cannot be read blocks the call. A call decided before a stop is re-checked just before its credential is minted and ends `not_executed` (`agent_stopped`). Decisions for a non-active agent carry `agent_state:<state>`. Migration 017 adds `agent_states` (the database also refuses undoing a revocation and a self-approved change). Cedar: `agent-restricted` now forbids only the actions with an external effect, and the new `agent-stopped` forbids all; 18 properties are proven (two new) and 9 weakened variants caught. **Nothing in the product changes a state yet**: the operator API, the CLI and maker-checker reinstatement are K1-3, signed state records K1-2. The API's hard-coded `AgentState::Active` is gone.

### Added

- **The agent kill switch is usable (K1-3a, ADR-013).** Operator API: `POST /v1/agents/{agent_id}/restrict | quarantine | revoke` (Cedar action `stop_agent`, admins; one principal; takes effect from the agent's next call; **only ever tightens**: a weaker state is refused, the same stop again is not a change) and `GET /v1/agents/{agent_id}` (`read_agent_state`). Bringing an agent back is a change request, kind `reinstate_agent`, that a second principal approves (`propose_reinstate_agent` / `approve_reinstate_agent`); its apply is idempotent on the request's id across the two stores, any other change of the agent since the proposal fails it closed, and a revoked agent cannot be reinstated. **Revoking** sets the state first and then revokes every mandate the agent holds (reason `manual`, delegations included); a repeat finishes a sweep that stopped half-way, and nothing can be issued or delegated to a revoked agent. The agent id must be one a passport names, exactly (404 otherwise). A global limit bounds stops, every attempt (refused ones too) is audited, and `kavach_agent_state_changes_total{to,result}` has three alerts. CLI: `kavach agent status | restrict | quarantine | revoke | reinstate`. A state record names the change request that carried out a loosening (`change_request_id`, optional in format 3). Migration 019.

### Changed

- **Every change of an agent's state is a signed record in the evidence chain (K1-2, ADR-013 §4); bundle format 3.** A new kind `agent_state` holds the agent, the change number, from and to state, a **closed `reason_code`** and a keyed digest of the operator's free text (the chain never holds the text), who changed it and, for a loosening, who approved it. A **tightening** takes effect first and its record follows (a reconciler writes it if the request could not; `kavach_agent_state_records_missing` and `…_reconciled_total`, alerts `KavachAgentStateRecordMissing` and `KavachAgentStateReconcilerStopped`); a **loosening** is written with its record in one transaction or not at all. Migration 018 adds the append-only `agent_state_changes` history (with a per-agent change number and database-level rules), widens the kind check and adds one-record-per-change. **`export` writes version 3; a verifier older than this release refuses a version 3 bundle.** `bundle-v1`, `bundle-v2` and `bundle-v2-digest` are unchanged; `bundle-v3` is new, and the spec and the independent verifier cover it. The store's reason became `reason_code` plus an optional `note`.
- **Mandate verification re-checks the mandate's form** (`Mandate::check_form`): format version, capability-reference subject, delegation depth, parent/depth agreement, channels, contact window inside the 08:00–19:00 IST floor, contact actions with a window, ceilings in range, lifetime 1 s to 30 days. Kavach issues mandates that satisfy these, so nothing it wrote is refused; a signed token that breaks them now is.
- **Revocation evidence names its event by a reproducible digest.** A `mandate_revocation` record now carries `event_digest` (`sha256-jcs-v1:` and the SHA-256 of the event's RFC 8785 bytes, the token's payload) instead of `event_sha256`, which hashed the event in Rust struct order and could not be reproduced from the specification. **Records written before this release keep `event_sha256` and still verify**; `bundle-v1` and `bundle-v2` are byte-identical, `bundle-v2-digest` is new. A record must state exactly one, well formed; both, neither or a malformed one is refused. A verifier older than this release refuses a record with `event_digest` (a missing member), it does not misread it. A retried event stored in the old form is still recognised as a retry (both digests are computed for the comparison). No migration: the stored column holds either form.
- **The bundle verifier refuses a member name used twice in one object** and a record whose `hash_alg` is not `v2` (both found by the independent verifier; the specification already required it). Bundles Kavach itself writes are unaffected.
- **The system-of-record listener refuses an event for a tenant the stack does not serve** (400), before it is verified or acted on. Revocations were already scoped by the event's tenant; such an event used to be accepted and revoke nothing.
- **Development fixture (`kavach init`):** each development borrower now holds one loan, `lms:loan/<borrower id>` (it was one per event), so a payment reaches every mandate issued for the borrower. The default world gains a second borrower, `ref:borrower:B-ATTACK` (its own consent and synthetic destinations), which `kavach attack` uses for the revocation attacks; nothing is ever sent to it. Projects made before this release need `kavach init --force`.
- **Evidence bundle format 2 (R1b-3, ADR-012 §7).** `export` writes version 2, which carries records of every kind in `records.jsonl`: decisions and `mandate_revocation` records, in one chain, with checkpoints covering both. Verifiers (`kavach-evidence verify-bundle`, `kavach evidence verify`, `kavach why --bundle`) read versions 1 and 2. They refuse a kind they do not know, by file and line, and never skip it; a version 1 bundle may hold decisions only. Bundles written before (version 1) still verify; a verifier older than this release refuses a version 2 bundle. `kavach why` on a revocation's record id says it is not a decision. New test vector `bundle-v2`; `bundle-v1` is unchanged.
- **Database (migration 015):** the agent evidence table can hold more than one kind of record (R1b-1, ADR-012 §7). Every existing row is a decision (`kind = agent_decision`, equal to the kind in its signed payload); a revocation record (`mandate_revocation`) is identified by its system-of-record event. The database enforces each kind's fields, one record per chain position, one decision per request and one record per event. Grants and the append-only triggers are unchanged. Nothing writes the new kind yet.
- **Changed (agent API): a retry after an `unknown` outcome gets that outcome back, replayed.** Retrying a `request_id` whose first call ended `unknown` (sent, result not known) now returns `200` with the stored reply, `outcome: unknown` and `replayed: true`. It used to return 409. So an agent stops retrying, and the case goes to reconciliation. 409 `in_flight` now means only that the first call is still running. A retry still never mints a credential or sends again (the Stripe idempotency model).
- **Breaking (API): `GET /v1/models` writes an in-house model's `origin` as `in_house`**, the same as model records, `GET /v1/models/{model_id}` and evidence. It used to write `inhouse`. The list's `status`, `risk_tier` and `governance_mode` are unchanged; they now come from the same types as the rest of the API.
- **Breaking (API errors): every refusal is now an RFC 9457 problem, `application/problem+json`**, on the operator, agent and system-of-record listeners. The body has `type` (`/problems/<code>`, relative), `title`, `status`, `detail`, a stable `code`, a `fix`, and the request's `request_id`. 401s carry `WWW-Authenticate`, and 429s and 503s carry `Retry-After`. Unknown paths and wrong methods are problems too (404, 405), where they used to be empty bodies.
  - **The old `error` member stays through v0.1**, holding the same text as `detail`. Clients that check for `application/json` on errors must accept `application/problem+json`.
  - **A 5xx no longer returns its cause:** `detail` is generic, and the cause is logged (redacted) under the `request_id`.
  - **Refusals no longer quote the caller's input.** JSON and JSON Schema errors name the field and the rule it failed, never the value. Until now, an evaluate input that failed its schema came back with the offending value in the 400, and the operator API's body and query rejections were axum's plain text, which can quote values.
  - `kavach` commands show the problem's `code` and `request_id`.
- **Breaking (dev evidence): evidence written under `kavach dev up --at` now says `time_sync: dev_fixed` instead of `synced`.** Every hand-set clock is marked, and the offline verifiers (`verify-bundle`, the agent chain verifier) refuse `dev_fixed` records and checkpoints unless told they are verifying a development stack (`--dev`). This is a second refusal next to the one for `dev-` keys.
- **Breaking (dev stack): `kavach dev up`'s operator API needs the project's operator token** (`.kavach/operator.jwt`), checked by Cedar with the bundled policies. Before, any local process, or a web page using DNS rebinding, could call it. Every `dev up` listener now refuses a Host header other than `localhost`, `127.0.0.1` or `[::1]` (421) and the self-asserted `X-Kavach-Principal` header (401). `kavach` commands send the token. Projects made earlier get their access-control files (`.kavach/kavach/cedar/`) on the next `dev up`. The attack catalog is now version 2, with the agent-token and no-token attacks on the operator route.
- **Breaking for anyone recomputing evaluate evidence hashes: `DecisionEvent` schema 1.1.0 hashes `decision_time` and `evaluated_at` at microsecond precision.** They used to be hashed with nanoseconds, but Postgres keeps microseconds, so an event read back from the database did not hash to its stored hash and could not be re-checked. Both stores now truncate the two timestamps before hashing, so what is stored is what was hashed.
  - **The hash rule is unchanged** (same fields, same canonical order); the canonical form of the two values changed, hence the minor version.
  - **Records at 1.1.0 or later must re-verify exactly.**
  - **Pre-1.1.0 records** still verify wherever their nanoseconds survive, and mixed chains verify; nothing is re-fingerprinted. Read back from Postgres, a pre-1.1.0 record that fails only as lost precision explains is reported as **legacy: cannot be re-checked**. `kavach-evidence verify` exits 2 with a warning: never "verified", and not called tampered.
  - **No downgrade:** a pre-1.1.0 record after a 1.1.0 one is refused.
  - **Pilots should re-baseline:** export, then start a fresh chain.
  - **Independent verifiers** must truncate the two timestamps first.
  - See `docs/DECISION_EVENT_COMPAT.md`.
- **Breaking (evaluate API): a consent whose purpose differs from the request's is now a recorded BLOCK with `CONSENT_MISMATCH`, as ADR-001 §7 step 4 and §9 specify.** Until now, `POST /v1/evaluate`, gRPC and batch refused such a request as a validation error (400 / `INVALID_ARGUMENT` / a `validation_error` row) before any decision, and wrote no evidence. Now it gets a decision and an evidence row. In shadow mode the returned decision is PASS, with `policy_decision` BLOCK. The engine applies the check itself, so a pack without a consent rule still blocks a mismatch. Callers that treated the 400 as "consent refused" should read the BLOCK instead.
- **Breaking (evaluate API): a request with no `consent` object is also a recorded BLOCK with `CONSENT_MISMATCH`** (the pack's code for an absent consent), because ADR-001 §9 makes presence an engine check. `consent` is now optional in the request: HTTP and batch used to refuse a missing field as malformed, and gRPC refused it with `missing consent`. A consent object that is present but malformed, for example without `timestamp`, is still refused. The decision's evidence holds `input_digest` only, never the raw input.
- Log redaction leaves canonical UUIDs and full RFC 3339 timestamps whole. The number rule masked fractional seconds and about one UUID in five, so record and mandate ids in the logs couldn't be searched. The match is strict: a lowercase versioned UUID with at least one letter, and a timestamp with `T`, a zone, a 19xx/20xx year, no word character on either side, and a value that parses. Phone, Aadhaar and PAN numbers beside or glued to such spans are still masked.
- **Policy engine: the CEL implementation moved from `cel-interpreter` 0.10 to `cel` 0.14.5** (the same project under its current crate name). It returns syntax errors where the old parser panicked (an incomplete expression such as `a &&`). **Treat this as a policy change:** a change in the engine's semantics changes what a signed pack decides even when the pack's bytes do not. Every golden fixture and scenario test gives the same decisions as before; run your own pack tests before upgrading. Kavach's own guards stay: panics in the CEL crates are contained, packs are bounded at load, and evaluation has a wall-clock timeout.
- **Agents: references are held to a published format.** A reference-only parameter (`ref:<type>:<id>`) may hold at most 8 digits in total, however spread, and nothing that reads as a PAN (ADR-004 §7). Anything else is a recorded BLOCK (`raw_identifier:<field>:<kind>`). Systems of record should issue short counters or random letters, not hex or numeric ids. PANs and Aadhaar numbers are now detected in every string parameter.
- **Breaking (configuration): connections to Postgres require verified TLS.** `kavach-api`, `kavach-batch` and `kavach-evidence export` / `checkpoints` now connect with `sslmode=verify-full`: TLS, a certificate that chains to a trusted root, and a matching host name. A deployment whose Postgres serves no TLS, or whose database URL names a weaker `sslmode`, no longer starts.
  - **Postgres:** enable TLS (`ssl = on`, `ssl_cert_file`, `ssl_key_file`) with a certificate that names the host in your database URLs. Prefer a DNS name; an IP address works only if the certificate lists it. Use `hostssl` lines in `pg_hba.conf` so the server refuses plaintext too.
  - **Kavach:** if the certificate comes from a private CA, set `--database-ca <pem>` / `KAVACH_DATABASE_CA` (API and batch; also `kavach-evidence export`). Remove any `sslmode=` weaker than `verify-full` from `KAVACH_DATABASE_URL`, `KAVACH_MIGRATION_DATABASE_URL` and `KAVACH_AUDITOR_DATABASE_URL`. `PGSSLMODE` in the environment is ignored.
  - **Pilot compose stack (`deploy/docker-compose.pilot.yml`):** its Postgres now serves TLS only and refuses plaintext. Before `docker compose up`, run `scripts/pilot-db-tls.sh` once: it writes `deploy/pilot-db-tls/` (a certificate for `postgres`, its key, and `ca.pem`, which Kavach verifies with; the CA key is not kept). With your own PKI, put `server.crt`, `server.key` and your CA as `ca.pem` there instead. An existing pilot database keeps its data; only the server's TLS settings change.
  - **Development:** plaintext needs both `--insecure-dev` (export commands: `--allow-plaintext-database`) and `sslmode=disable` in the URL. `kavach-batch` gains `--insecure-dev` for this. The flag alone downgrades nothing.
- **Breaking (configuration):** the agent data plane now requires a checkpoint signing key. Startup fails without `--checkpoint-keys-dir` (`KAVACH_CHECKPOINT_KEYS_DIR`); the key id defaults to `kavach-checkpoint-1` (`--checkpoint-key-id`).
  - Create it with `kavach-keys generate` in a key directory, as for the other keys.
  - It must not share an id with the mandate, evidence or credential key, or key material with the evidence key.
  - A `dev-` key is accepted only with `--insecure-dev`. Development bundles from `kavach-dev generate` already include `dev-checkpoint-1` and its settings; regenerate older bundles.
  - Deployments that do not enable the agent data plane are unaffected.

- The `kavach-evidence` binary moved to the new `kavach-evidence-cli` crate. Its name and its `verify` command are unchanged; build it with `-p kavach-evidence-cli` instead of `-p kavach-evidence`.
- The API refuses to start if its mandate, evidence, checkpoint or credential key id starts with `export-` (or `dev-export-`): those ids are reserved for evidence export keys.
- The evidence commit makes fewer database round trips: 6 instead of 9 for a recorded allow, 3 instead of 5 while it holds the partition lock. Same transaction, lock order and durability.
- Bearer tokens (API callers and agents) are checked against keys decoded once per JWKS load or refresh, rather than on every request. Acceptance rules are unchanged.

### Added

- **Agent-only mode (Phase 0).** `--agent-only` serves the agent surfaces and the operator surface of the agent path, and none of the credit track (evaluate, packs, models, decision events, retention, incidents, batch, the console, the gRPC evaluate service, and credit change requests). It is for hosted builds and refuses to start without the agent surfaces. The *Network isolation* job's stack runs with it. It removes the way to reach the credit track, not the code (the tables stay, and are not tenant-keyed: ADR-014).
- **Alert rules and a dashboard (Phase 0).** `deploy/monitoring/` ships Prometheus alert rules (checkpoint stall and lag, skipped checkpoints, a revocation without its evidence record, a stopped reconciler, outcome write failures, a credential id conflict, unknown outcomes, a slow commit stage, service down, and more) and a Grafana dashboard. The thresholds are starting points. A test fails if a rule or panel names a metric the API does not register.
- **Orderly stop (Phase 0).** On SIGTERM or Ctrl-C `kavach-api` stops accepting connections, lets requests in flight finish, waits for every gateway call that has started (up to `--shutdown-grace-seconds`, default 30), writes a final checkpoint and exits 0. If a listener or a call has not finished by the deadline it logs `ALERT shutdown was not clean` and exits 1. `docker-compose.pilot.yml` gets `stop_grace_period: 45s`. Not built: a readiness drain before the stop.
- **`kavach simulate`: payments and disputes (R1c-3, ADR-012).** A scenario may list system-of-record `events:` (`loan.paid`, `loan.disputed`, `loan.dpd30` for a new default), each for the first borrowers whose messages are delivered. The oracle refuses every call under a mandate issued at or before a borrower's payment or dispute, from the event on (from the scenario alone). Reconciliation checks that each event revoked exactly the mandates the run held, that the evidence holds one signed revocation record per event naming them, and, from the provider's inbox, that nothing was delivered under a revoked mandate after its event. New built-ins `payment-stops-contact` and `dispute-stops-contact`; `mixed-week` gains a payment. Revocation is no longer listed as not covered.
- **Attack catalog version 4 (R1c-2, ADR-012 §8): 30 attacks.** Eight revocation attacks against a borrower kept for them (`ref:borrower:B-ATTACK`): forged, stale, future-dated, unknown type, another tenant, wrong loan, reaching forward, and replayed. Each is judged on the reply and on ground truth: the attack mandate must still authorise, and a refused event must leave no revocation record in the evidence chain (an accepted event that should have been refused is a breach). They run in process (memory and Postgres, also either side of midnight IST) and in `kavach attack`; a project without the attack borrower makes them inconclusive (exit 2, fix `kavach init --force`), never a pass. A test breaks each defence in turn and shows its attack judged `succeeded`.
- **`GET /v1/agent-revocations/{system}/{event_id}`:** the evidence record of a revocation by event, for `read_evidence` holders, rate limited and audited before it is returned, like `GET /v1/agent-decisions/{record_id}`.
- **`kavach sor event --type loan.paid|loan.disputed` (R1c-1, ADR-012).** Sends a signed payment or dispute for a borrower's loan, dated now on the stack's clock: every mandate issued for the loan up to now is revoked, with its delegations, and the command prints the revoked ids. `loan.dpd30` (the default) assigns, as before. There is no option to backdate an event.
- **Revocations are evidence (R1b-2, ADR-012 §7).** Every revocation by a system-of-record event is a signed `mandate_revocation` record in the agent evidence chain, between the decisions: the event (system, id, type, content hash, time), the revoked mandates, `revoked_at` and `recorded_at`. The loan is named only by a keyed pseudonym. The request that revokes writes it; if it cannot, a background reconciler writes it, once per event, and `kavach_revocation_records_missing` with an `ALERT` log line reports any still missing. Chain verification accepts both kinds and refuses any kind it does not know. Migration 016 adds an index for the reconciler.
- **Revocation by system-of-record event (ADR-012, R1a).** A signed `loan.paid` or `loan.disputed` event on `POST /v1/sor/events` revokes every active mandate issued about that loan at or before the event, and every mandate delegated from them; the reply lists them (`revoked`). The event must come from a registered system-of-record issuer, verify, be fresh and pass the replay guard. A retry of the same event gets the stored result (`replayed: true`); the same event id with different content is refused (409). Each revocation is kept (append-only, migration 014) and audited.
- **The gateway re-checks the mandate just before minting a credential.** A mandate revoked between the decision and the send ends the call `not_executed` (`mandate_revoked`): no credential, nothing sent.
- `kavach simulate` S3: every run reconciles three records, its own ledger, Kavach's evidence bundle and the provider's inbox. The inbox is the one record Kavach does not write, so it gives the provider's own proof that each allowed message arrived exactly once (never twice), that nothing blocked or refused arrived, and that each message went to its borrower's own destination. Any finding fails the run. Built-in scenarios name the SECURITY_PROPERTIES.md rows they exercise (`covers:`), and a test fails if a row is renamed or removed.
- `kavach simulate` S2:
  - **Adversarial agent:** makes the attack catalog's tool-call attacks (raw identifiers, another borrower, forged mandate, unregistered tools and values), on borrowers kept for it.
  - **Retries:** agents can send the same request again after an unknown outcome (`retry_rate`).
  - **Provider failures:** the first borrowers can be given a destination where the provider refuses (422), errs (500) or loses the response (`provider_failures`).
  - **Oracle:** now judges the registry, plain references, the mandate's subject, forward-once retries (409 `in_flight` after an unknown outcome) and provider outcomes (a 5xx is unknown).
  - **Six new built-in scenarios**, including `mixed-week`.

- CLI output prints known digest fields whole (`input_digest`, and the Cedar and registry digests in `why`). Before, the number rule masked any digest that happened to contain ten digits in a row. ### Not yet

- Truncation and rewrites are detected only by verifying an export against a checkpoint the operator copied off-host; the live database is not checked continuously, and nothing is anchored outside the operator's own storage.
- A deleted outcome row is detected only against an earlier signed bundle that contains it.

### Fixed

- **A gateway call no longer dies with its client.** The call used to run inside the request handler, so a client that disconnected between "sent" and "outcome recorded" cancelled it: the allow was left without an outcome (`outcome_missing`) and its retry was refused as in flight. The call now runs in a task of its own, counted while it runs, and completes whether or not the client is still there. `kavach dev up` also waits for calls in flight before its final checkpoint and export.
- `kavach attack` can run again on the same stack: request and event ids carry a per-run suffix (a second run used to be refused with 409 for reusing them), and on a fixed clock a run moves to a fresh day when an earlier run used the day's contacts.

- Request bodies with free-form JSON (`/v1/evaluate`, `/v1/authorize`, `/v1/tools/{tool}`, change proposals) refuse the key `$serde_json::private::RawValue` anywhere, escaped forms included (400). serde_json would otherwise read its value as a string of JSON, so Kavach would act on a different structure than other parsers see in the same bytes.
- A CEL rule that makes the third-party CEL parser or interpreter panic no longer crashes Kavach: the pack is refused at load (`CelCompile`), and a panic during evaluation is an evaluation error, recorded as a BLOCK. A trailing `&&` was enough to make the parser panic. Found by the `cel_policy` fuzz target.
- Canonical JSON (everything signed or hashed as evidence) refuses objects with the key `$serde_json::private::RawValue`. serde_json, with the `raw_value` feature that axum and sqlx switch on, parses an object whose first key is that token as a string of JSON, so its canonical form (which sorts `$` first) would not parse back to itself. Found by the `jcs_differential` fuzz target. No signed type can carry such a key today.
- Bearer tokens (API callers and agents) whose JOSE header is not a UTF-8 JSON object are refused (RFC 7515 §4). Before, the JWT library skipped unknown header members without checking their bytes. Found by the `agent_token` fuzz target; only a key the identity provider holds could sign such a token.
- HMAC v2: the timestamp skew check no longer overflows on an extreme `X-Kavach-Timestamp`. Builds with overflow checks panicked before the signature was checked; release builds wrapped, so one timestamp value passed the skew check (the signature was still required).
