# Changelog

Notable changes to Kavach. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Kavach is pre-alpha: there are no releases yet, and anything may change before v0.1.

## [Unreleased]

### Added

- **Encrypted reference envelope and local key rotation, eighth approved store slice.** Added an AES-256-GCM destination codec that authenticates tenant, subject reference, channel, record version and key id; owner-only local key files; and explicit decrypt-only previous keys. The resolver still uses its fixture, and Postgres persistence/API selection remain pending.
- **Transactional consent withdrawal and mandate revocation, seventh approved store slice.** A verified withdrawal now updates immutable history and `consent_current`, revokes every active root referencing that consent and its children, and appends a durable revocation row in one transaction under the issuance lock. A failed revocation write rolls back the consent change; retries return the stored revoked set. Root issuance is blocked by the recorded withdrawal, and the revocation records whether Kavach's clock met its configured sync bound. API selection and credential notification remain pending.
- **Transactional signed consent grants, sixth approved store slice.** A verified, tenant-bound grant appends immutable authority history and advances `consent_current` atomically. Exact update-ID retries are idempotent and conflicting payloads are refused. No API route selects these stores yet.
- **Transactional signed preference storage, fifth approved store slice.** Verified contact-preference updates now atomically append immutable history and advance the Postgres current projection. Identical update-ID retries are idempotent; conflicting payloads are refused. A late opt-out can stop contact, while re-allowing after opt-out remains withheld pending an explicit ordering rule. API selection remains pending.
- **Signed authority update verifier, fourth approved store slice.** Added a canonical JWS envelope for consent grants/withdrawals and contact preference changes. It checks issuer key registration for the exact tenant and source, record scope, and trusted-time freshness for permissive changes; restrictive changes remain admissible when late or clock-unsynced. Transactional persistence and live enforcement remain pending.
- **Read-only pilot authority projections, third approved store slice.** Migration 033 creates immutable consent/preference update history and tenant-scoped current records. Postgres read adapters reject corrupt or mismatched projections. Runtime receives read-only grants; signed updates, live withdrawal, and gateway selection remain pending.
- **Contact-preference contract, second approved store slice.** Added a tenant, subject and channel scoped record with validity bounds and explicit allow/opt-out status. The lookup helper denies missing, expired, opted-out or mismatched records, and the development memory adapter rejects malformed or duplicate records. Gateway enforcement and persistent records remain pending.
- **Consent fixture contract, first approved store slice.** Local consent records may now carry information types, validity start, data date range and explicit status. Existing fixtures remain readable; malformed richer records fail API startup, and mandate issuance waits for the validity start. The generated development fixture includes the richer subset. The benchmark config now supplies the existing disabled review-snapshot defaults needed to compile. Persistent consent, preferences and encrypted references follow the accepted plan.
- **D17 live proof reuse refusal.** The console-to-agent integration now retries approval after a successful decision and verifies that the consumed exact-action step-up proof cannot create a second approval (`409`) on either memory or least-privilege Postgres.
- **D17 live approval refusal checks.** The memory and least-privilege Postgres console-to-agent integration now proves that changing the approved waiver amount conflicts, while repeating the original request without release IDs remains `HUMAN_REVIEW` despite the reviewer's live session.
- **D17 Postgres live-flow coverage and migration repair.** The console sign-in, step-up, approval and agent release integration now runs against both memory and an isolated least-privilege Postgres schema. Unique migration versions 029–031 replace colliding later 026–028 filenames; migration 032 restores the challenge and snapshot grants after the runtime-grant refresh. The storage build script makes new migration files visible to incremental builds.
- **D17 live console approval integration.** The OIDC integration test now follows console sign-in through the exact-action step-up callback and approval creation, then verifies agent release, signed evidence, replay and altered-action refusal. The step-up handler uses the console session clock consistently; the OIDC double honors the requested ACR in the `claims` parameter. OpenAPI now documents the approval route, and its contract checker prefers a literal route over a parameterized route.
- **D17 committed proposal evidence.** `proposal` trust tools now record and return the policy decision without reference resolution, provider credential issuance, dispatch or provider outcome. Acceptance verifies a committed `HUMAN_REVIEW`, encrypted snapshot persistence and no provider send; it also seeds an approved record to verify release-to-agent execution, exact evidence semantics, replay and altered-action refusal on memory and Postgres. The live console/passkey ceremony remains separately covered.
- **D17 status documentation.** Updated the authorization ADR, installation guide and review ledger to reflect completed release consumption, credential binding and console decisions, while keeping the full acceptance chain and independent IdP/security review open.
- **M4 D17 console decision controls.** The exact-action review now submits explicit approve/reject decisions through the existing session-bound endpoint. An approved result displays the short-lived approval and execution IDs with the unchanged-request handoff instruction; rejection is shown as non-executable. The server remains responsible for passkey proof, Cedar authorization, auditing and approval creation.
- **M4 D17 release consumption and credential authorization.** The agent gateway consumes the durable approval release for the authenticated, extracted exact action. The core rechecks the release against the source signed HUMAN_REVIEW evidence and reevaluates current policy; only a still-matching HUMAN_REVIEW is lifted. The resulting signed record preserves `policy_decision=HUMAN_REVIEW`, records the allowed returned decision and original action digest, and uses the release's one-use credential ID for broker issuance. Missing or invalid release data remains non-forwardable.
- **M4 D17 release-to-credential binding.** An immutable release now carries the approval's one-use credential ID, and a database insert guard verifies that the release matches the consumed, live approval row. A new migration backfills existing releases; Postgres tests reject forged or modified release evidence.
- **M4 D17 execution-ID handoff and evidence idempotency.** Agent request envelopes now accept `execution_id` alongside `approval_id`; both stay outside action parameters and the exact-action hash. Evidence storage keys retries by the execution ID while the signed record retains the original reviewed `request_id`; retries for the same execution replay its record, and mismatched binding conflicts. Authorization consumption and credential use of the release remain pending.
- **M4 D17 explicit approval release record.** An approved review now retains its source HUMAN_REVIEW record ID and receives a separate server-generated execution ID. The store atomically consumes the approval and appends an immutable, tenant-scoped release record; retrying the same execution returns that record, while a different execution cannot reuse the approval. The original request ID and action hash remain unchanged. Agent execution and evidence idempotency using this ID are still pending, so this slice does not authorize tool calls.
- **M4 D17 approval creation endpoint.** `POST /auth/human-review/{record_id}/approval` reloads the signed exact-action review, requires Cedar permission and a one-use matching session step-up proof, audits before inserting a five-minute approval record, and returns its opaque `approval_id`. Agent requests accept that validated optional envelope field; authorization consumption remains pending, so the identifier does not yet grant authority.
- **M4 D17 approval-store runtime selection.** `AppState` now selects the existing memory approval adapter for local/test workflows and the Postgres adapter when durable storage is configured. The API exposes the selected store internally; authenticated approval and credential/authorization wiring remain pending.
- **M4 D17 review snapshot key rotation.** The active key seals new snapshots; repeatable decrypt-only previous keys open live envelopes by authenticated key id. Duplicate ids/material are refused, hardening checks every key file, and the runbook documents overlap and retirement.
- **M4 D17 reviewer step-up (console).** The loaded exact-action review now offers explicit passkey step-up initiation and redirects to the IdP URL returned by the API. The UI states that step-up alone does not approve or release the action.
- **M4 D17 reviewer display (console).** Agent Evidence now provides a role-aware manual lookup and read-only rendering of the audited exact-action projection; it introduces no decision-record listing or approval control.
- **M4 D17 expired snapshot cleanup.** The API purges expired encrypted review snapshots at startup and every 60 seconds; deletion remains expiry-gated by the store and cleanup stops with the existing server shutdown signal. Cleanup errors are logged and retried at the next interval.
- **M4 D17 reviewer read endpoint.** Added authenticated `GET /auth/human-review/{record_id}` for the `approver` permission and live console session. It verifies the tenant-scoped evidence signature, exact action digest and 30-minute expiry, returns only reviewer display fields, and audits before returning; general evidence routes remain unchanged.
- **M4 D17 encrypted snapshot storage.** Added a ciphertext-only store port, volatile development adapter, and tenant-scoped Postgres table for encrypted action projections. The gateway now persists committed `HUMAN_REVIEW` projections when the snapshot key is configured, with a 30-minute lifetime; retries decrypt and compare instead of overwriting. The table supports live reads and expiry cleanup, rejects updates, and blocks deletion before expiry.
- **M4 D17 snapshot key loading.** Added `--review-snapshot-key-file` / `KAVACH_REVIEW_SNAPSHOT_KEY_FILE` for a stable 32-byte hex AES key and `--review-snapshot-key-id` / `KAVACH_REVIEW_SNAPSHOT_KEY_ID` for envelope rotation metadata. The key is zeroized on drop and owner-only mode is checked under `--require-hardening`.
- **M4 D17 encrypted review snapshot primitive.** Added a versioned AES-256-GCM envelope for the exact-action review projection, authenticated against tenant, HUMAN_REVIEW record id and signed action digest. Decryption recomputes the digest before a reviewer can use the projection. HSM/key rotation and reviewer reads remained pending at that point; the primitive does not alter the evidence chain or grant authority.
- **M4 D17 step-up callback route.** Mounted `GET /auth/step-up/callback`: it requires the one-time callback cookie, verifies state and the initiating live session, exchanges the code with PKCE, verifies the signed ID token and consumes the challenge once. The verified exact-action proof is retained only in that server-side session for a later one-time approval use. The callback never grants approval; the approval endpoint and credential/authorization wiring remain pending.
- **M4 D17 step-up initiation route.** Mounted `POST /auth/step-up/{record_id}` behind the live console session and CSRF checks. It authorizes the `approve_human_review` Cedar action, loads and signature-verifies a tenant-scoped HUMAN_REVIEW record with its exact-action binding, starts the configured Keycloak ACR/PKCE flow, and returns an authorization URL with a one-time opaque callback cookie. Callback routing, approval API and credential/authorization wiring remain pending.
- **M4 D17 API challenge-store wiring.** `AppState` now retains the existing memory challenge store for development and the Postgres challenge store for configured durable storage, exposing the selected backend for the planned HTTP adapter. One-use challenge storage is available at runtime, but no step-up route is mounted yet.
- **M4 D17 ACR configuration.** Added optional `--console-step-up-acr` / `KAVACH_CONSOLE_STEP_UP_ACR`, validated to a bounded non-control value and retained in console login settings for future route wiring. It does not enable step-up or approvals by itself; the IdP must map the value to WebAuthn and the routes remain pending.
- **M4 D17 tenant-scoped review lookup.** The dataplane now loads candidate HUMAN_REVIEW evidence only through its configured tenant and returns no record for a foreign tenant, a non-review outcome, or a missing exact-action digest. Signature verification remains required before step-up context is derived; HTTP route wiring remains pending.
- **M4 D17 reviewer authorization.** Added the Cedar `approve_human_review` action for the `approver` role (and the existing `superadmin` catch-all) after the owner approved extending `approver` on 2026-11-17. The IdP `change-approvers` group alias is unchanged. Role matrix tests and Cedar formal-analysis coverage include the new boundary.
- **M4 D17 review evidence signature check.** Step-up context derivation now uses the existing single-record evidence verifier to check payload hash and Ed25519 signature against a caller-supplied trusted key set, honoring the explicit development-key policy. Invalid or unknown signatures are refused before step-up context is built. The tenant-scoped Dataplane loader now handles record lookup; the HTTP route must still enforce reviewer roles.
- **M4 D17 server-derived step-up context.** A helper builds `StepUpRequest` only from a tenant-matched `HUMAN_REVIEW` record with a self-consistent payload hash and exact-action digest, plus a source-qualified reviewer read from a live console session. Callers must verify the record signature before using the helper. No route or reviewer-role check is mounted yet.
- **M4 D17 signed review-action binding.** Committed `HUMAN_REVIEW` agent evidence now includes the versioned exact-action digest, computed from the authenticated agent, tenant, signed tool-registry digest and extracted action. Only the digest is persisted; canonical parameters remain transient and zeroized. The field is optional and omitted on older records to preserve their canonical bytes. If binding cannot be produced, the decision fails closed to `BLOCK`. Reviewer lookup/route wiring remains pending.
- **M4 D17 callback context custody.** The session-bound callback flow now retains the challenge's tenant and exact action digest alongside its reviewer and OIDC secrets. A future callback handler can derive verifier expectations from server-held flow state, not browser-supplied action fields. Route mounting and obtaining the initial action from a trusted HUMAN_REVIEW record remain pending.
- **M4 D17 callback-session custody.** Pending Keycloak callback secrets are bound server-side to the initiating live console session and source-qualified reviewer. The browser receives only a random, one-time callback handle; the main `SameSite=Strict` session cookie is unchanged. Wrong-state callbacks do not consume the flow, while successful lookup is one-use. Callback HTTP routing, action resolution and PAR/request-object protection remain pending.
- **M4 D17 Keycloak callback verifier.** Added bounded authorization-code exchange with sensitive client authentication and PKCE S256, exact session/reviewer/tenant/action binding, signed ID-token checks, and atomic challenge consumption only after successful verification. The service is not mounted on a callback route; browser session custody and PAR/request-object protection remain pending.
- **M4 D17 Keycloak challenge initiation.** Added a step-up authorization request builder that persists state/nonce digests and action/reviewer context before redirect, requests the configured ACR as essential, sets `max_age=0`, and uses PKCE S256. Callback session custody, code exchange and token verification wiring remain pending; the builder is not mounted on an API route.
- **M4 D17 durable step-up challenge state.** Added memory and PostgreSQL stores for nonce/state digests and the tenant, reviewer and action binding. Callback state lookup is expiry-scoped, consumption is atomic and one-use, and only expired rows can be purged. The stores are not yet connected to a Keycloak callback or approval route.
- **M4 D17 OIDC step-up claim verifier.** Added strict validation for a signed step-up ID token: issuer, audience, nonce, expected reviewer subject and ACR, and `auth_time`/`iat` at or after the challenge. This verifies claims only; Keycloak challenge initiation/configuration, approval API and authorization wiring remain pending.
- **M4 D17 step-up boundary and test double.** Added the step-up provider port and a testkit-only fake. Challenges and verified results bind the tenant, authenticated source-qualified reviewer, exact action digest and expiry; invalid, expired and replayed synthetic proofs fail. No WebAuthn/Keycloak adapter or approval route is active.
- **M4 durable approval storage.** Added a tenant-scoped PostgreSQL approval table and memory/PostgreSQL store implementations. Consumption is one atomic update, bound to the exact action hash and trusted current time; approval IDs and credential IDs are unique, records cannot be edited or deleted, and replay, rejection, mismatch and expiry return no approval. The store is not wired to reviewer authentication, step-up or credential issuance.
- **M4 approval-record contract.** Added the PRD FR-6 record shape with strict digest and decision/credential validation plus exact tenant/action and expiry checks. Its persistence and atomic consumption are now implemented by the M4 durable-storage slice; reviewer authentication, step-up, authorization wiring and credential issuance remain pending.
- **M4 exact-action binding primitive.** Added a versioned, domain-separated SHA-256 digest over tenant, authenticated agent identity, tool-registry digest, mandate, request ID, action and typed parameters. Canonical transient bytes are zeroized and extraction violations are refused. This primitive is not wired to an approval flow and cannot grant authority; M4 remains partial.
- **M4 HUMAN_REVIEW fail-closed regression slice.** A waiver above the mandate ceiling is verified to produce a persisted `HUMAN_REVIEW` record with no allow grant. The WebAuthn step-up, action-hash-bound approval, reviewer surface and single-use credential remain pending; acceptance scenario 6 remains partial.
- **ADR-015 local-only gateway-held adapter fixture.** The dataplane integration test now uses an explicitly local fake adapter and verifies both a simulated delivery and a lost response recorded as `unknown`. The credential-accepting forwarder is bypassed in both cases. This fixture sends no network traffic and is not shipped or enabled by the API.
- **ADR-015 OpenBao KV v2 secret-store adapter.** Added read-only, send-time secret lookup through the existing provider-secret port. It enforces HTTPS except for loopback development, bounds responses, rejects unsafe mount/reference paths, disables redirects, and returns only the `token` field. Local fake-server tests cover the wire path and authorization header; the adapter is not wired into runtime provider dispatch.
- **ADR-015 gateway-held dispatch seam.** The dataplane can select an injected provider set for internal credential issuance and tokenless forwarding. Providers outside that set keep the provider-verifiable route. A fake-forwarder integration test proves selected sends do not call the credential-accepting adapter. The API supplies no gateway-held configuration yet, and no external provider is enabled.
- **ADR-015 internal credential artifact.** Added an object-safe `InternalCredentialBroker` capability that signs and encrypts a request-bound artifact to a fresh Kavach-only key, discards the key and token, and returns only a credential-id/expiry receipt. It requires no provider encryption key and is not wired to gateway sends. Provider-verifiable issuance remains unchanged.
- **ADR-015 provider-neutral groundwork.** Added a gateway adapter request context for resolved destination/channel/template data, an object-safe provider-secret port, and a development file secret store restricted to owner-only files. A local fake-server test confirms the existing credential-accepting path still sends one authenticated empty-body request and does not serialize the resolved destination or template fields. No third-party provider adapter is selected or implemented; see ADR-015 for remaining provider setup gates.
- **ADR-017 R3a unknown-outcome demo.** `kavach demo` now runs the built-in mock-provider scenario with a lost response and provider error, verifies both signed resolutions against provider ground truth, and checks the provider inbox for no resend. ADR-017 records the simulator/demo point as complete; real-provider mapping remains gated by ADR-015.
- **ADR-017 R3b delivered-attestation core.** The authorization core can append a signed one-person `confirmed_delivered` operator resolution from a reason code, reference digest, and source-qualified identity; repeats are idempotent and the caller never provides the reference itself.
- **ADR-017 R3b delivered-attestation change request.** The `operator` role can propose a digest-bound request and complete it themselves; the API stores and audits only the reference digest, and approval binds to the unknown outcome and its existing resolution history.
- **ADR-017 R3b not-delivered attestation.** A second operator identity must approve the frozen request; both source-qualified identities and only the reference digest enter the signed resolution/audit. The integration test confirms it cannot resend or release contact slots.
- **ADR-017 R3b conflict closure.** A two-person, digest-bound change request names the confirmed governing state for an existing conflict. The regression test checks same-person refusal, source-qualified identities, digest-only audit, preserved conflict history and no resend.
- **ADR-017 R3b security attacks.** Regression coverage proves altered resolutions fail signature verification, certificate and same-person approvals are refused, and attestations neither resend nor release contact slots. The simulator oracle now checks delivered and not-delivered attestations and conflict closures against provider ground truth rather than requiring the recorded source to be provider status.
- **On-demand ADR-017 outcome review in Agent Evidence (UI-3, fourth slice).** Admins can load and cursor through unknown outcomes, see their governing state and source, and inspect the complete resolution history. Loading, empty, error, retry and role-hint states follow the console plan. This remains a read-only surface.
- **Audited ADR-017 unknown-outcomes API (UI-3, third slice).** `GET /v1/unknown-outcomes` provides a tenant-scoped cursor page of signed unknown outcomes, resolution history and the governing state. It requires `read_evidence`, uses the existing rate limit, and records each read before returning data. It cannot resend or release a contact slot.
- **ADR-017 operator-review store read (UI-3, second slice).** Memory and Postgres agent evidence stores now provide a tenant-scoped, credential-id cursor-paged read of every unknown outcome with its action and complete signed resolution history. It includes all governing states; the reconciler's narrower work queue is unchanged.
- **ADR-017 resolution history in agent evidence lookup (UI-3, first slice).** `GET /v1/agent-decisions/{record_id}` now includes every signed resolution for an unknown outcome, oldest first, under the existing `read_evidence` authorization, rate limit and audit. The Agent Evidence page displays each resolution's state, source, reason code, people, digest and signature record. The later on-demand outcome list is recorded in the third-slice entry above.
- **Console role-aware navigation and Users & roles (ADR-019 step 3, complete).** The console reads `/v1/me` once per signed-in caller in memory, uses known groups and assigned roles as page-visibility hints, and shows the persistent superadmin banner. `/users` provides the searchable, cursor-paged directory, active role bindings, grant and revoke change proposals, and an on-demand audited access review with CSV download. The API remains the authorization gate and audit source.
- **Propose role grants from Users & roles (ADR-019 step 3).** A role-capable viewer can open a grant proposal for a principal in the directory. The request contains the selected role and that principal's issuer/subject; success reports the pending change request and states it grants no access until a different authorized person approves. Failures retain the dialog and show the API problem. The UI is a hint, and the API enforces authorization, self-grant and escalation rules.
- **Propose role revocations from Users & roles (ADR-019 step 3).** A role-capable viewer can propose revocation of an active binding. The request contains the binding id; success reports the pending change request and states the binding stays active until a different authorized person approves. Failures retain the dialog and show the API problem. The API enforces authorization and protects the last person-bound administrator.
- **On-demand access review and CSV download (ADR-019 step 3).** `/users` loads an access review only after the operator requests it, showing binding subject, role, grant proposer and approver, last-seen time and stale status, while naming policy alias groups without expanding IdP membership. JSON reads and CSV downloads use the API's audited route; export failures retain API problem details. CSV serialization and spreadsheet formula protection stay on the API.
- **Reading roles and the access review (ADR-019 step 2c, part 2).** Four new read endpoints, all additive:
  - `GET /v1/principals` (`read_principals`): the people who have signed in to the tenant, a page at a time (`limit`, `cursor`), with `?q=` matching the display name or subject, ignoring case.
  - `GET /v1/role-bindings` (`read_principals`): active bindings, and ended ones with `?include=ended`.
  - `GET /v1/access-review?format=json|csv` (`read_access_review`): one row per active binding, with who proposed and who approved the grant and when the person was last seen. A person last seen more than `--access-review-stale-days` ago (`KAVACH_ACCESS_REVIEW_STALE_DAYS`, default 90, 1–3650), or never, is marked stale. The alias groups are named, not expanded. Every export writes an `export_access_review` audit row first; an export that cannot be audited is refused (503). CSV fields are always quoted, and a field starting with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading `'`.
  - `GET /v1/me`: the caller and the roles bound to them now. Any authenticated caller; it decides nothing.
  - The role reads require their corresponding Cedar read actions; alias groups do not get these permits. All four answer with `Cache-Control: no-store`.
  - The console calls `GET /v1/me` for role-aware presentation, `GET /v1/principals` for the directory, `GET /v1/role-bindings` for active assignments and `GET /v1/access-review?format=json|csv` for the on-demand audited review and CSV download.
- **Granting and revoking roles (ADR-019 step 2c, part 1).** Two new change kinds: `grant_role` `{role, subject: {kind, issuer, value}}` and `revoke_role` `{binding_id}`. They go through `POST /v1/change-requests` and need a second person to approve. The binding is written or ended only inside the approval's transaction, so a pending grant gives nothing.
  - **Who may change roles:** only `superadmin` and `user_admin` may propose or approve a role change, and only a `superadmin` may touch `superadmin` (Cedar receives the role as context).
  - **No self-grant:** neither the proposer nor the approver may grant a role to themselves or to a group in their token. The approver is refused with the request left pending.
  - **Conflicts (409):** a duplicate active binding, and a revoke that would leave the tenant with no active person binding for `superadmin` or `user_admin`. Both are checked at proposal and again at approval, under a per-tenant lock on Postgres, so two concurrent revokes of the last two superadmins cannot both pass.
  - **Validation:** a subject must use the configured OIDC issuer (or, with `--insecure-dev`, the development header source, people only), with a value of 1–512 characters and no control characters.
  - **Approval-time read failures:** a database read failure while re-checking an approval now returns 503 and leaves the request pending instead of failing it.
- **Operator roles decide requests (ADR-019 step 2b).** Cedar gains the `Kavach::Role` entity and one set of policies per role, following the ADR-019 matrix. The `admins`, `change-approvers`, `operators` and `viewers` groups keep their permissions. Every authorisation reads the caller's bindings for the tenant, with no cache; if they cannot be read, the request gets 503. A person binding matches the token's `sub` under the configured issuer. A decision only `superadmin` allows writes `acting_as_superadmin: true` to its audit row. `kavach-cedar-analysis` proves four operator properties, including that only `superadmin` may change `superadmin`. The new actions `propose_/approve_grant_role`, `propose_/approve_revoke_role`, `read_principals` and `read_access_review` have no endpoints yet (step 2c). Operators making OIDC requests are recorded in `principals` (`last_seen_at` moves at most hourly) for the coming access review; this record never decides anything.
- **Operator role storage and the superadmin bootstrap (ADR-019 step 2a).** Migration `024_operator_roles.sql` adds `principals` and `role_bindings` (per tenant; a binding names a person or a group, ends but is never deleted; the runtime role cannot change a binding's role, subject or grant time, nor delete either table's rows) and a nullable `admin_audit_log.acting_as_superadmin`. `AuditEntry` gains `acting_as_superadmin` (additive; false for every existing row). `kavach-api --bootstrap-superadmins` (`KAVACH_BOOTSTRAP_SUPERADMINS`) writes exactly two OIDC people as the tenant's first superadmins, once, while none is active; see INSTALL. Roles are stored and looked up but do not yet change any authorisation decision (step 2b).
- **ADR-019, operator roles and role management (accepted, design only).** It defines:
  - seven roles (`superadmin`, `user_admin`, `policy_admin`, `approver`, `operator`, `auditor`, `viewer`) with a role-to-action matrix;
  - per-tenant bindings to an OIDC subject or an IdP group, which Cedar receives alongside the token's groups;
  - grants and revokes as maker-checker change requests (`grant_role`, `revoke_role`), with no self-grant and no revoking the last `superadmin` or `user_admin`;
  - a two-person, one-time `superadmin` bootstrap, with superadmin-only decisions flagged in the audit;
  - a principals directory that stores issuer, subject and display name only;
  - an access-review export in CSV and JSON.

  Sign-in stays with the IdP and Kavach stores no passwords. The `admins`, `change-approvers`, `operators` and `viewers` groups keep exactly their current permissions, as aliases. SCIM is out of scope. Nothing is implemented yet: [docs/ADR-019-operator-roles.md](docs/ADR-019-operator-roles.md).

- **`scripts/demo.sh`: one command to a seeded Kavach with the console signed in.**
  - **What it does:** builds the console and the binaries from the current tree, then starts kavach-api on `127.0.0.1:8080`, with Postgres evidence, Cedar and console sign-in, plus the OIDC test double and the mock provider. It seeds what the console's real-stack tests use, then prints the URL, one test user per Cedar group (`demo-admin`, `demo-approver`, `demo-operator`, `demo-viewer`) and how to stop.
  - **Postgres:** it needs a Postgres it can reach (default `postgres://kavach@127.0.0.1:55433/postgres`, or `KAVACH_DEMO_DATABASE_URL`). It never starts one: if it can't reach one, it prints the start command. Each run gets its own `kavach_demo_<epoch>` schema, and `scripts/demo.sh stop` drops only that schema.
  - **Local state:** in `.demo/` (owner-only, git-ignored). No Docker.
  - **Picking the user:** the OIDC test double's new `--pick` mode makes each sign-in show a "Sign in as" page listing every user (static HTML, no script, `Cache-Control: no-store`, a `default-src 'none'` CSP).
  - **Docs and CI:** documented in the README quick start and `docs/INSTALL.md`. In CI, a fresh clone of the commit runs demo.sh against the Postgres service, and `npm run test:demo` (`console/e2e/signin.demo.ts`) signs in as each user through that page and opens every page.
  - **Scope:** a development tool only, with `--insecure-dev` and a test identity provider that signs in whoever picks a name.
- **A CI check that the console calls every API operation, or says why not.** `scripts/console_path_coverage.py` (Python standard library only) reads every method and path in `docs/openapi.yaml` and fails unless `console/src` calls it with that method (tests, test fixtures and the generated `openapi.d.ts` are not read) or `console/api-coverage-exempt.txt` lists it with a reason. An exemption for an operation the spec no longer has, or one the console now calls, fails too. It runs, with its own unit tests, first in the "Format, Clippy, Test" job.

On an agent-only server the sidebar leaves out the credit-track pages (Evaluate, Policies, Models, Batch jobs, Incidents, Retention, Decision events), their paths show "Not served on this server" without calling the API, and Overview drops the model, jurisdiction and credit capability cards. - **An OIDC test double** (`crates/kavach-api/tests/support/oidc_double.rs`) for the console sign-in tests, also runnable for local development and browser tests: `cargo run -p kavach-api --example oidc_double -- --client-secret-file <file> --jwks-out <file>`. - **`GET /v1/agents?state=&limit=&cursor=`.** Lists every agent a passport names in the stack's tenant, with its state (`AgentStateView`; `active`, change 0, for one never changed), in ascending agent-id order. Keyset paging: `limit` defaults to 50 and is clamped to 1-200, `next_cursor` (the last agent id considered) is null when nothing follows; `state` filters. Admins only (`read_agent_state`, no policy change); another tenant's passports are never listed. A store that cannot be read is a 503, never "active". For the console's agent list (UI-1).
- **Listener limits and HSM call deadlines (roadmap 1.2).** Every listener (operator HTTP, gRPC, agent, system of record) now has a TLS handshake timeout (`--tls-handshake-timeout-seconds`, default 10, 1–60), a header read and idle deadline that trickled bytes do not extend (`--header-read-timeout-seconds`, default 10, 1–120), a request timeout answered with a `503` RFC 9457 problem (`unavailable`, `request_id`, `Retry-After: 5`; gRPC `CANCELLED`) and never with a partial decision (`--request-timeout-seconds`, default 30, 1–300), and a per-listener in-flight cap that refuses at once with `503` and `Retry-After` instead of queueing (`--max-in-flight-requests`, default 256, 1–65536; gRPC `UNAVAILABLE`). Each HSM sign and health call has a deadline (`--hsm-timeout-ms`, default 5000, 100–60000) and fails closed when the token does not answer. No setting turns a limit off; startup refuses a value outside its bounds. **Behaviour changes:** before this, plain HTTP and gRPC had no header or request timeout and gRPC had no TLS handshake timeout, so a slow client could hold a connection open indefinitely. Keep-alive connections and gRPC channels idle for longer than the header read timeout are now closed by the server (clients reconnect). With the agent surfaces, the start is refused when `--request-timeout-seconds` does not exceed `--provider-timeout-ms` or `--hsm-timeout-ms` (a deployment with a provider timeout of 30 s or more must raise the request timeout). gRPC TLS is now terminated by the same rustls configuration as HTTP (ring provider, same client-certificate verifier), offering only `h2`. No wire format, evidence format or migration change. Settings are in [INSTALL.md](docs/INSTALL.md#kavach-api).
- **`kavach-api --require-hardening` (`KAVACH_REQUIRE_HARDENING`).** An opt-in startup check that refuses to start, listing every failed condition at once and exiting 78 (`EX_CONFIG`), when: any relaxation in the bypass inventory is active; the API listener has no TLS; the TLS key, the subject-pseudonym key or the HSM PIN file is readable by group or others (on a platform that cannot verify file modes it refuses rather than skips); or a provider endpoint is plain HTTP (no loopback exception) or carries userinfo, a query or a fragment. The refusal names a provider by scheme, host and port only, never userinfo, path or query. Under the flag `POST /v1/dev/clock` is not mounted. `/v1/runtime` (and the OpenAPI) reports `require_hardening`. For deployments that set it, it closes the plain-HTTP-provider risk accepted in the privacy review of 2026-10-15. `kavach-api` only; `kavach-batch` follows separately. Without the flag nothing changes. **The HMAC secret** is an inline value (`--hmac-secret`), not a file, so it has no file-mode check; only its length (at least 32 bytes) is checked.
- **New relaxation `memory_evidence_store`.** The in-memory evidence store (`--evidence-store memory`) is now reported as a relaxation in `/v1/runtime`, in `kavach_relaxation_active{relaxation="memory_evidence_store"}` and in the OpenAPI enum. **Alerting note:** a deployment on the memory evidence store used to report no relaxation and now reports this one, so `KavachRelaxationActive` (critical) fires for it. Move to Postgres, or silence that label knowingly.
- **Outcome resolutions, phase R1a (ADR-017).** A second signed row that refers to an `unknown` outcome (never a rewrite of it, never a resend): `confirmed_delivered`, `confirmed_not_delivered` or `ambiguous`, from a provider status, an operator attestation (delivered needs one person, not delivered two), a two-person conflict resolution, or the reconciler. New `AgentEvidenceStore::record_resolution` and `resolutions`, a pure `governing()` that computes the state from all of an outcome's resolutions (no "latest wins": two different confirmed answers are `Conflicted`, ambiguity never overrides a confirmed state), the form rules enforced by every store, migration 023 (`agent_outcome_resolutions`, append-only; the read-only auditor role may read it), and a store contract that runs on memory and on Postgres as the runtime role. Nothing writes resolutions yet and nothing exports them: the bundle (format 4) and both verifiers are R1b, the mock status endpoint and the reconciler are R2.
- **A permanent Rust-versus-Python verifier-agreement test** (`the_rust_and_python_verifiers_agree_on_a_real_exported_bundle`). A dev stack is taken through a decision, a refusal, a payment (a revocation record) and an agent stop (an `agent_state` record), stopped so that it exports, and both `kavach evidence verify` (library) and `conformance/kavach_verify.py` read the bundle: they must agree on the record, outcome and checkpoint counts, the last sequence number and the not-protected findings; then six kinds of damage must each be refused by both. It needs `python3` (CI fails without it instead of skipping). It replaces the one-off local check; ADR-017 will change the bundle format, and this is what keeps the two verifiers agreeing as it does.
- **Alerts for the revocation audit entry and snapshot staleness.** `kavach_revocation_audit_entries_missing`, `kavach_revocation_audit_entries_written_total` and `kavach_revocation_audit_last_pass_timestamp_seconds` (the S3 reconciler used to log only) with the alerts `KavachRevocationAuditEntryMissing` and `KavachRevocationAuditReconcilerStopped`; `KavachSnapshotNotRunRecently` (warning; silent until a first run). A test now proves that a refused issuing on an unsynchronised clock moves `kavach_sor_events_unavailable_total{kind="issuing"}` and that a revocation on that clock does not. The monitoring README lists the failures that are silent by design and the alert for each.
- **Snapshot reconciliation (ADR-012 addendum).** `POST /v1/reconciliation/closed-records` and `kavach reconcile <file>`: the lender sends the loans it considers paid or disputed, with the time each was closed; Kavach returns the live mandates still held for them. A mismatch (a mandate for a paid loan processed at or before the closure, or any live mandate for a disputed loan) means a payment or dispute event most likely never arrived; it is the only thing that can find that. It **reports and revokes nothing**: resend the signed event or stop the agent. New Cedar action `reconcile_closed_records` in the operator policy (admins; covered by startup schema validation and the authorization tests: a non-admin, an agent token and no credentials are refused; the cvc5 analysis covers the agent policies, not this), a rate limit (six a minute), an audit entry by counts, the gauge `kavach_snapshot_mismatches` and the alert `KavachClosedLoanWithLiveAuthority`. Nothing runs it on a schedule.

### Security

- **Numbers in any script's digits are detected (F1).** The detector of raw identifiers in tool parameters mapped digits to ASCII from twelve blocks only (fullwidth, nine Indian scripts and the two Arabic-Indic sets), so a mobile number, an Aadhaar number or a long digit run written in, for example, Thai, Khmer, Myanmar, NKo, Adlam or mathematical bold digits passed it, in any parameter and in reference-only fields. It now maps every Unicode decimal digit (general category Nd): the 77 digit blocks of Unicode 17.0, the version of the pinned toolchain's character tables, in a static sorted table with a binary search and no new dependency. Tests: every `char` checked against the table, the table checked against std's numeric characters (a toolchain bump that changes the Unicode version fails until the table is derived again), a Thai mobile number through separators and mixed scripts, and a property test over all blocks and separators. Still not detected: numbers written with numeric characters that are not decimal digits (superscripts, subscripts, circled numbers, Roman numerals), spelt out in words or encoded (bypass inventory). A tool call that carried such a number before is now a recorded BLOCK.
- **Startup errors no longer echo a provider endpoint or JWKS URL in full.** A provider endpoint that does not parse, or carries userinfo, a query or a fragment, was printed whole in the `kavach-api` startup error, and a JWKS URL that could not be fetched was printed whole in the startup error and in the refresh warning; a credential in the URL reached stderr or the log. Both now name the endpoint by scheme, host and port only, or say only that it does not parse. `kavach-api` only; no configuration or format change.
- **Console sign-in, backend (ADR-018 option C).** Off unless `--console-client-id` (`KAVACH_CONSOLE_CLIENT_ID`) is set; without it nothing changes and the session cookie is never read. When set, `kavach-api` acts as a backend-for-frontend: `GET /auth/login` starts an OIDC authorization code flow with PKCE (S256), `state` and `nonce`; `GET /auth/callback` exchanges the code (confidential client, `client_secret_basic`), verifies the ID token (`iss`, `aud`, `nonce`) and checks the access token with the existing operator OIDC verifier, then sets an HttpOnly, Secure, SameSite=Strict `__Host-kavach_session` cookie. The IdP tokens stay in server memory; the browser holds only a random handle. Also `GET /auth/session`, `GET /auth/config` and `POST /auth/logout` (refresh token revoked; an IdP end-session URL only with `--console-idp-logout`, never with `id_token_hint`). `GET /auth/session` names the principal and the groups the server's Cedar policy evaluates it in (the token's groups merged with its memberships in the entities file, sorted), or `null` groups when no policy is loaded; they are for display only. On the operator listener only, a session cookie counts as a credential when the request carries `X-Kavach-Console: 1`, a same-origin `Origin`/`Sec-Fetch-Site` and no `Authorization` or principal header; it is then authorized by the same Cedar policy as a CLI token of that person. The agent listener refuses it and the SoR listener never reads it. Idle limit (default 15 min, 5-60) and absolute limit (default 8 h, at most 12 h); a refresh never extends the absolute one, and a failed refresh ends the session. A full session table (default 1000, at most 10 000) refuses a new login rather than evicting one. Login and logout are written to the existing audit log (`console_login`, `console_logout`; no migration). Startup refuses an incomplete or unsafe configuration: no operator OIDC, a client id equal to an API audience, a non-HTTPS redirect URI or IdP endpoint outside `--insecure-dev`, `offline_access`, a discovery document naming another issuer, limits out of bounds; under `--require-hardening` also a client secret file readable by group or others, and the pasted-token sign-in. Sessions live in one process's memory: a restart signs everyone out, and replicas do not share them. The OpenAPI changes are additive. Not included: the console's sign-in screen.
- **Security headers on API responses (roadmap 1.3).** Every response of the operator, agent and system-of-record HTTP listeners now carries `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Referrer-Policy: no-referrer` and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (the API serves no HTML), successes and problems alike, including 401, 404, 405 and the routers' fallback problems. One layer (`http::api_security_headers`) on each router; it keeps a header a response already sets, so the console's responses keep the console's policy and per-file cache policy. No API route set a cache policy before, so none is overridden. No body, status or format change. Not covered: the `kavach dev up` guard's own 421 and 401 refusals, and gRPC.
- **`rustls-webpki` 0.103.15 to 0.103.17 (RUSTSEC-2026-0382, certificate verification may accept distrusted intermediates).** A lockfile-only patch update: no source, configuration or format change, and no other package moved. The library verifies the chain of a TLS client certificate (the operator API's mTLS principal path) and of the servers Kavach connects to over TLS. Local result, CI could not run: `cargo deny check advisories` no longer lists it.
- **`tokio` 1.53.1 to 1.53.3 (RUSTSEC-2026-0386, `AsyncFd::new` and related constructors violate I/O safety).** A lockfile-only patch update (the package's version and checksum; no other package or dependency edge moved). Every listener and the provider client run on tokio.
- **`zstd` 0.13.3 to 0.13.5, `zstd-safe` 7.2.4 to 7.4.1, `zstd-sys` 2.0.16 to 2.1.3 (RUSTSEC-2026-0391, -0398, -0403, -0410).** A lockfile-only update within semver: these three packages move and no dependency edge changes. The only dependent is `polars-arrow`, as an optional dependency that no feature enables: zstd is in no build graph (`cargo tree -p kavach-batch --all-features` lists none), and the `kavach-batch` tests pass unchanged.
- **`libsqlite3-sys` (RUSTSEC-2026-0459) recorded as the one ignored advisory in `.cargo/audit.toml`.** Not compiled: it is in `Cargo.lock` only, through `sqlx-sqlite` (an optional dependency of sqlx 0.8.6 that no feature enables; `cargo tree -e features -i sqlx-sqlite` prints nothing), and it cannot be updated because `sqlx-sqlite` 0.8.6 requires `libsqlite3-sys` 0.30. Review by 2027-02-14, or when sqlx is upgraded. `deny.toml` keeps `ignore = []`: `cargo deny` checks the build graph and does not flag it. Still reported as warnings: `rustls-pemfile` and `unsafe-libyaml` (unmaintained).

### Fixed

- **The console says when the Kavach API is not reachable.** A call that never completed, or a 5xx with no `request_id`, showed a raw status such as "GET /auth/config failed (500) · no request_id was returned". Every problem kavach-api sends carries a `request_id`, so these come from something in front of it: typically the Vite dev proxy with nothing on `:8080`. The console now says "The Kavach API is not reachable. Start it with scripts/demo.sh (or check that kavach-api runs on :8080)." In a built console (served by kavach-api itself) it says to check that kavach-api runs and that any proxy in front of it can reach it. The status and "no request_id was returned" line stay below it. A 4xx without a `request_id`, and any response with one, are shown as before. Console only; no API change.
- **A batch I/O failure marks the job failed (L20).** An output write that failed mid-run left the job recorded as `running` for good, and an output flush that failed (the `kavach-batch` command flushed only after the job was marked done) left it `completed` over a short or empty file. Now any error after the job is created (reading the input, writing or flushing the output, recording the `running` status, an evaluate error) marks it `failed`, once; the worker flushes the output before it marks a job completed. `error_summary` is now a fixed description (`output could not be written`, `input could not be read`, `input line N is not a valid request`, `job status could not be recorded`, `evaluate failed...`), never a path, a record's contents or an error's own text: a parse failure used to store serde's message, which can quote the line. The command's own error on stderr is unchanged. If the job store also refuses to mark the job failed, there is no retry: the job keeps its last recorded status (`pending` or `running`), the run returns its original error, and a warning names the job by id. Model setup (the input schema) is now checked before the job is created, so a run that never starts records no job. No API, schema or evidence change.
- **A poisoned runtime lock no longer panics every request that reads it (roadmap 1.5).** `AppState::runtime()` used `.expect`, so after any panic while that lock was held, `GET /v1/runtime`, `/v1/packs`, `/v1/models` and every change request panicked (the connection dropped with no response). It now returns the 500 problem (`internal`), as the evaluate lock already did. An approval refused this way leaves the change request pending, and an approval now reads the runtime view before carrying out a reinstatement, so nothing is changed first. Both locks log one `ALERT` line the first time they are found poisoned, naming the lock only, never the request. A poisoned evaluate lock refuses every decision (500, nothing recorded) until the process is restarted; routes that do not need it are still served. `AppState::runtime()` now returns a `Result` (Rust API only; no wire change).
- **The Rust verifier refuses a member a line does not define (verifier agreement).** The generated-history test found that `kavach evidence verify` ignored an unknown member in `records.jsonl`, `outcomes.jsonl` and `checkpoints.jsonl` (it hashed only the members it knew), while the independent Python verifier refused it, so a bundle with unsigned data in an outcome or a checkpoint, sealed by someone holding the export key, passed one verifier and not the other. Both now refuse it as `read` (spec §2.1, an explicit member list per file and record kind; the Python verifier refused a record's extra member as `chain`, now `read` too). No format change: the version 1 to 4 vectors verify unchanged and the exporter writes only the listed members (a test ties each list to the struct it serializes). A bundle that held an undefined member, which no Kavach exporter writes, no longer verifies.
- **Upgrade note (migrations 020, 021, 022).** All three are additive and nullable (`mandate_revocations.clock_synced`, `admin_audit_log.idempotency_key`, `mandates.source_occurred_at`, an index on revocations by record). Rows written before them read back with the new fields unknown; scope for an older root stays `nbf`. A binary from before them cannot start against the migrated database (it refuses migrations it does not know); roll back by dropping the columns first. The B2 guarantee holds only once every replica runs the new version.
- **A payment that arrives out of order with its default stops contact either way round (B2, ADR-012 addendum).** A revocation was scoped by `nbf`, the time Kavach processed the default, so a payment that occurred after a default but arrived after it was processed did not stop it, and a default that arrived after its payment issued a live mandate. Now: a revocation reaches every root whose source time (the issuing event's `occurred_at`, kept in `mandates.source_occurred_at`, migration 022) is at or before the payment's, with a 30 s skew margin; a recorded payment closes the record to earlier events (a barrier, checked atomically with the insert), clamped to receipt + 5 minutes so a source clock that runs ahead cannot hold it closed; a dispute holds the record against new mandates (no release path yet). A payment dated ahead is accepted, not refused. Attack catalog 8 (35 attacks): `future-revocation` removed, `replayed-revocation` orders its events apart. Existing mandate rows keep `nbf`. An issuing event may be dated at most 60 s ahead (T1; 300 s into the past as before).
- **A revocation's audit entry is never lost to a failed write (S3, ADR-012 addendum).** The entry was written after the commit and only logged on failure, so a crash or an unavailable admin store left the audit log short and nothing repaired it. It is now derived from the stored revocation and written once per event (`admin_audit_log.idempotency_key`, migration 021), by the request or by a reconciler that pages through the stored rows. The entry carries `clock_synced` as stored (S4).
- **Authority is issued only on a synchronised clock (S4, ADR-012 addendum).** Making a mandate from an event, and delegating one, now fail closed (503, `Unavailable`) when the clock is not synchronised within 500 ms, the bar the gateway already held a decision to; the mandate service ignored sync status before. Nothing is spent, so the event is retried when the clock recovers. A revocation still applies on any clock, without evaluating the future bound against that clock (a clock that is behind would otherwise refuse a genuine payment as future-dated), and is flagged: `mandate_revocations.clock_synced` (migration 020, nullable), the audit entry and a warning log. New metric `kavach_sor_events_unavailable_total{kind}` and alert `KavachSorEventsUnavailable`; one clock-error bar (`DEFAULT_MAX_CLOCK_ERROR_MS`) for the data plane and the mandate service.
- **A revoking event is applied in one step (B3, ADR-012 addendum).** Revoking and recording the revocation were separate operations, one transaction per root, and the replay guard was spent first. A crash or an unavailable database part-way left some mandates live, and the retry was refused as a replay. The store's new `apply_revocation` revokes every root and its delegations and writes the revocation row in one transaction, under the tenant's mandate lock; a revoking event no longer consumes the time-limited replay guard (its single use is the stored revocation); a failed attempt changes nothing and its retry completes. A new store method, so an adapter outside this repository must implement it (the contract is in `mandate_store::conformance`).
- **A payment (or dispute) event that reaches Kavach late still stops contact (B1, ADR-012 addendum).** Revoking events had the same 300 s freshness window as issuing events, so a `loan.paid` delivered ten minutes late was refused, nothing retried it, and contact continued. A revoking event now has no maximum age; an event from the future, and an old *issuing* event, are still refused. It is scoped by its own `occurred_at` (it never reaches a mandate issued after it) and its single use is the permanent stored revocation, which is now looked up before the (24 h) replay guard, so a repeat after a day revokes nothing. Attack catalog version 7: `stale-revocation` is replaced by `late-revocation` (accepted, revokes nothing newer); the independent verifier and the specification say the same. Still open: B2 (a payment before the default it follows) and B3 (a crash between revoking and recording).

### Changed

- **The console is served in agent-only mode, with security headers, and only from a real build.** `--agent-only` now serves the console's static files (no new route: its credit-track pages answer the unknown-path 404 there). Every console response carries a strict Content-Security-Policy (`default-src 'self'`, no inline script or style, `frame-ancestors 'none'`, `base-uri 'none'`, `form-action 'self'`), `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`; the page is `no-store` and hashed assets are cached for a year (`immutable`). An unknown `/v1/...` path and a missing file are now the 404 problem instead of the console page. `build.rs` embeds `console/dist` only when its `index.html` loads a script from `/assets/` and every asset it names exists, so a stub no longer embeds a blank page; a binary without the console answers `/` with a plain "console not built" page (404). API responses get their own headers (see Security, roadmap 1.3).
- **Breaking (configuration): `--hmac-secret` / `KAVACH_HMAC_SECRET` must be at least 32 bytes.** A shorter secret now stops the start with a message naming the length (never the secret); there is no exemption for `--insecure-dev`. Generate one with `openssl rand -hex 32`. Signatures are unchanged for any secret that is accepted. No fixture, dev config or script in the repository set a short secret (`kavach dev up` sets none; `scripts/pilot-phase3.sh` reads `PILOT_HMAC_SECRET` from the operator's environment).
- **Breaking (configuration): each system-of-record issuer key is registered for one tenant and one system (ADR-014 §2.1).** `sor_issuers` entries need `tenant_id` (a file without it does not load). An event is accepted only from a key registered for its own tenant and system; one tenant's key can no longer sign for another on a shared stack. An unknown key id, another tenant's key and a bad signature are refused with the same message (`the event is not accepted from this issuer`), and the detail goes to the redacted log only. Startup refuses a key id used twice and the same public key under two ids or two tenants. Existing projects: add `tenant_id` to each issuer, or run `kavach init --force` (a development project needs the new second issuer key for the `issuer-for-another-tenant` attack; without it the attack is inconclusive, never a pass).
- **Attack catalog version 6 (36 attacks):** `issuer-for-another-tenant` (an event signed by another tenant's registered key, judged on the attack mandate and the evidence chain). The mandate vector gains `tenant_id` on its issuers and a `binding_refused` list, verified by `conformance/kavach_verify.py`.

### Added

- **Kill-switch attacks and simulation (K1-3b, ADR-013 §5).** Attack catalog version 5 (35 attacks): `quarantined-agent-acts`, `restricted-agent-contacts`, `reinstate-without-approval`, `self-approved-reinstate`, `certificate-principal-approves`. Each stops the holder agent, attacks the stop, and brings the agent back through the real approval path; judged on the reply and on ground truth (the state read back, nothing minted). `kavach simulate` gains `agent.restrict | quarantine | revoke | reinstate` events, an oracle model of agent state that shares no code with Kavach's, a reconciliation of each change against the evidence's signed records, and the built-in scenario `rogue-agent-quarantined`. The property row *A stopped agent does nothing…* is **Enforced**: the attacks ran on memory and on Postgres in CI. **Projects made before this release need `kavach init --force`:** the kill-switch attacks and reinstatement scenarios need the approver token it writes (`approver.jwt`; the development operator token now also holds the approver role, so that only the distinct-identity rule refuses its own approval); without it they are inconclusive (exit 2), never a pass.

- **Public specifications, `docs/specs/`** (evidence bundle format 2, credential format, mandate and system-of-record event) and an **independent verifier**, `conformance/kavach_verify.py`: Python, standard library only, written from the specification text alone. It verifies the published bundle, checkpoint, JCS, credential, mandate and event vectors and refuses unknown record kinds; CI runs it as the job "Independent verifier".

### Added

- **Agent risk state is enforced (K1-1, ADR-013).** An agent is `active`, `restricted` (reads within its mandate, nothing with an external effect), `quarantined` or `revoked` (nothing). The state is read from the database at every authorization, together with the state of every holder in the mandate's delegation chain, so a mandate delegated from a stopped agent authorises nothing while its parent's holder is stopped; a quarantine suspends mandates without changing them. A state that cannot be read blocks the call. A call decided before a stop is re-checked just before its credential is minted and ends `not_executed` (`agent_stopped`). Decisions for a non-active agent carry `agent_state:<state>`. Migration 017 adds `agent_states` (the database also refuses undoing a revocation and a self-approved change). Cedar: `agent-restricted` now forbids only the actions with an external effect, and the new `agent-stopped` forbids all; 18 properties are proven (two new) and 9 weakened variants caught. **Nothing in the product changes a state yet**: the operator API, the CLI and maker-checker reinstatement are K1-3, signed state records K1-2. The API's hard-coded `AgentState::Active` is gone.

### Added

- **The agent kill switch is usable (K1-3a, ADR-013).** Operator API: `POST /v1/agents/{agent_id}/restrict | quarantine | revoke` (Cedar action `stop_agent`, admins; one principal; takes effect from the agent's next call; **only ever tightens**: a weaker state is refused, the same stop again is not a change) and `GET /v1/agents/{agent_id}` (`read_agent_state`). Bringing an agent back is a change request, kind `reinstate_agent`, that a second principal approves (`propose_reinstate_agent` / `approve_reinstate_agent`); its apply is idempotent on the request's id across the two stores, any other change of the agent since the proposal fails it closed, and a revoked agent cannot be reinstated. **Revoking** sets the state first and then revokes every mandate the agent holds (reason `manual`, delegations included); a repeat finishes a sweep that stopped half-way, and nothing can be issued or delegated to a revoked agent. The agent id must be one a passport names, exactly (404 otherwise). A global limit bounds stops, every attempt (refused ones too) is audited, and `kavach_agent_state_changes_total{to,result}` has three alerts. CLI: `kavach agent status | restrict | quarantine | revoke | reinstate`. A state record names the change request that carried out a loosening (`change_request_id`, optional in format 3). Migration 019.

### Changed

- **Every change of an agent's state is a signed record in the evidence chain (K1-2, ADR-013 §4); bundle format 3.** A new kind `agent_state` holds the agent, the change number, from and to state, a **closed `reason_code`** and a keyed digest of the operator's free text (the chain never holds the text), who changed it and, for a loosening, who approved it. A **tightening** takes effect first and its record follows (a reconciler writes it if the request could not; `kavach_agent_state_records_missing` and `…_reconciled_total`, alerts `KavachAgentStateRecordMissing` and `KavachAgentStateReconcilerStopped`); a **loosening** is written with its record in one transaction or not at all. Migration 018 adds the append-only `agent_state_changes` history (with a per-agent change number and database-level rules), widens the kind check and adds one-record-per-change. **`export` writes version 3; a verifier older than this release refuses a version 3 bundle.** `bundle-v1`, `bundle-v2` and `bundle-v2-digest` are unchanged; `bundle-v3` is new, and the spec and the independent verifier cover it. The store's reason became `reason_code` plus an optional `note`.
- **Mandate verification re-checks the mandate's form** (`Mandate::check_form`): format version, capability-reference subject, delegation depth, parent/depth agreement, channels, contact window inside the 08:00–19:00 IST floor, contact actions with a window, ceilings in range, lifetime 1 s to 30 days. Kavach issues mandates that satisfy these, so nothing it wrote is refused; a signed token that breaks them now is.
- **Revocation evidence names its event by a reproducible digest.** A `mandate_revocation` record now carries `event_digest` (`sha256-jcs-v1:` and the SHA-256 of the event's RFC 8785 bytes, the token's payload) instead of `event_sha256`, which hashed the event in Rust struct order and could not be reproduced from the specification. **Records written before this release keep `event_sha256` and still verify**; `bundle-v1` and `bundle-v2` are byte-identical, `bundle-v2-digest` is new. A record must state exactly one, well formed; both, neither or a malformed one is refused. A verifier older than this release refuses a record with `event_digest` (a missing member), it does not misread it. A retried event stored in the old form is still recognised as a retry (both digests are computed for the comparison). No migration: the stored column holds either form.
- **The bundle verifier refuses a member name used twice in one object** and a record whose `hash_alg` is not `v2` (both found by the independent verifier; the specification already required it). Bundles Kavach itself writes are unaffected.
- **The system-of-record listener refuses an event for a tenant the stack does not serve** (400), before it is verified or acted on. Revocations were already scoped by the event's tenant; such an event used to be accepted and revoke nothing.
- **Development fixture (`kavach init`):** each development borrower now holds one loan, `lms:loan/<borrower id>` (it was one per event), so a payment reaches every mandate issued for the borrower. The default world gains a second borrower, `ref:borrower:B-ATTACK` (its own consent and synthetic destinations), which `kavach attack` uses for the revocation attacks; nothing is ever sent to it. Projects made before this release need `kavach init --force`.
- **Evidence bundle format 2 (R1b-3, ADR-012 §7).** `export` writes version 2, which carries records of every kind in `records.jsonl`: decisions and `mandate_revocation` records, in one chain, with checkpoints covering both. Verifiers (`kavach-evidence verify-bundle`, `kavach evidence verify`, `kavach why --bundle`) read versions 1 and 2. They refuse a kind they do not know, by file and line, and never skip it; a version 1 bundle may hold decisions only. Bundles written before (version 1) still verify; a verifier older than this release refuses a version 2 bundle. `kavach why` on a revocation's record id says it is not a decision. New test vector `bundle-v2`; `bundle-v1` is unchanged.
- **Database (migration 015):** the agent evidence table can hold more than one kind of record (R1b-1, ADR-012 §7). Every existing row is a decision (`kind = agent_decision`, equal to the kind in its signed payload); a revocation record (`mandate_revocation`) is identified by its system-of-record event. The database enforces each kind's fields, one record per chain position, one decision per request and one record per event. Grants and the append-only triggers are unchanged. Nothing writes the new kind yet.
- **Changed (agent API): a retry after an `unknown` outcome gets that outcome back, replayed.** Retrying a `request_id` whose first call ended `unknown` (sent, result not known) now returns `200` with the stored reply, `outcome: unknown` and `replayed: true`. It used to return 409. So an agent stops retrying, and the case goes to reconciliation. 409 `in_flight` now means only that the first call is still running. A retry still never mints a credential or sends again (the Stripe idempotency model).
- **Breaking (API): `GET /v1/models` writes an in-house model's `origin` as `in_house`**, the same as model records, `GET /v1/models/{model_id}` and evidence. It used to write `inhouse`. The list's `status`, `risk_tier` and `governance_mode` are unchanged; they now come from the same types as the rest of the API.
- **Breaking (API errors): every refusal is now an RFC 9457 problem, `application/problem+json`**, on the operator, agent and system-of-record listeners. The body has `type` (`/problems/<code>`, relative), `title`, `status`, `detail`, a stable `code`, a `fix`, and the request's `request_id`. 401s carry `WWW-Authenticate`, and 429s and 503s carry `Retry-After`. Unknown paths and wrong methods are problems too (404, 405), where they used to be empty bodies.
  - **The old `error` member stays through v0.1**, holding the same text as `detail`. Clients that check for `application/json` on errors must accept `application/problem+json`.
  - **A 5xx no longer returns its cause:** `detail` is generic, and the cause is logged (redacted) under the `request_id`.
  - **Refusals no longer quote the caller's input.** JSON and JSON Schema errors name the field and the rule it failed, never the value. Until now, an evaluate input that failed its schema came back with the offending value in the 400, and the operator API's body and query rejections were axum's plain text, which can quote values.
  - `kavach` commands show the problem's `code` and `request_id`.
- **Breaking (dev evidence): evidence written under `kavach dev up --at` now says `time_sync: dev_fixed` instead of `synced`.** Every hand-set clock is marked, and the offline verifiers (`verify-bundle`, the agent chain verifier) refuse `dev_fixed` records and checkpoints unless told they are verifying a development stack (`--dev`). This is a second refusal next to the one for `dev-` keys.
- **Breaking (dev stack): `kavach dev up`'s operator API needs the project's operator token** (`.kavach/operator.jwt`), checked by Cedar with the bundled policies. Before, any local process, or a web page using DNS rebinding, could call it. Every `dev up` listener now refuses a Host header other than `localhost`, `127.0.0.1` or `[::1]` (421) and the self-asserted `X-Kavach-Principal` header (401). `kavach` commands send the token. Projects made earlier get their access-control files (`.kavach/kavach/cedar/`) on the next `dev up`. The attack catalog is now version 2, with the agent-token and no-token attacks on the operator route.
- **Breaking for anyone recomputing evaluate evidence hashes: `DecisionEvent` schema 1.1.0 hashes `decision_time` and `evaluated_at` at microsecond precision.** They used to be hashed with nanoseconds, but Postgres keeps microseconds, so an event read back from the database did not hash to its stored hash and could not be re-checked. Both stores now truncate the two timestamps before hashing, so what is stored is what was hashed.
  - **The hash rule is unchanged** (same fields, same canonical order); the canonical form of the two values changed, hence the minor version.
  - **Records at 1.1.0 or later must re-verify exactly.**
  - **Pre-1.1.0 records** still verify wherever their nanoseconds survive, and mixed chains verify; nothing is re-fingerprinted. Read back from Postgres, a pre-1.1.0 record that fails only as lost precision explains is reported as **legacy: cannot be re-checked**. `kavach-evidence verify` exits 2 with a warning: never "verified", and not called tampered.
  - **No downgrade:** a pre-1.1.0 record after a 1.1.0 one is refused.
  - **Pilots should re-baseline:** export, then start a fresh chain.
  - **Independent verifiers** must truncate the two timestamps first.
  - See `docs/DECISION_EVENT_COMPAT.md`.
- **Breaking (evaluate API): a consent whose purpose differs from the request's is now a recorded BLOCK with `CONSENT_MISMATCH`, as ADR-001 §7 step 4 and §9 specify.** Until now, `POST /v1/evaluate`, gRPC and batch refused such a request as a validation error (400 / `INVALID_ARGUMENT` / a `validation_error` row) before any decision, and wrote no evidence. Now it gets a decision and an evidence row. In shadow mode the returned decision is PASS, with `policy_decision` BLOCK. The engine applies the check itself, so a pack without a consent rule still blocks a mismatch. Callers that treated the 400 as "consent refused" should read the BLOCK instead.
- **Breaking (evaluate API): a request with no `consent` object is also a recorded BLOCK with `CONSENT_MISMATCH`** (the pack's code for an absent consent), because ADR-001 §9 makes presence an engine check. `consent` is now optional in the request: HTTP and batch used to refuse a missing field as malformed, and gRPC refused it with `missing consent`. A consent object that is present but malformed, for example without `timestamp`, is still refused. The decision's evidence holds `input_digest` only, never the raw input.
- Log redaction leaves canonical UUIDs and full RFC 3339 timestamps whole. The number rule masked fractional seconds and about one UUID in five, so record and mandate ids in the logs couldn't be searched. The match is strict: a lowercase versioned UUID with at least one letter, and a timestamp with `T`, a zone, a 19xx/20xx year, no word character on either side, and a value that parses. Phone, Aadhaar and PAN numbers beside or glued to such spans are still masked.
- **Policy engine: the CEL implementation moved from `cel-interpreter` 0.10 to `cel` 0.14.5** (the same project under its current crate name). It returns syntax errors where the old parser panicked (an incomplete expression such as `a &&`). **Treat this as a policy change:** a change in the engine's semantics changes what a signed pack decides even when the pack's bytes do not. Every golden fixture and scenario test gives the same decisions as before; run your own pack tests before upgrading. Kavach's own guards stay: panics in the CEL crates are contained, packs are bounded at load, and evaluation has a wall-clock timeout.
- **Agents: references are held to a published format.** A reference-only parameter (`ref:<type>:<id>`) may hold at most 8 digits in total, however spread, and nothing that reads as a PAN (ADR-004 §7). Anything else is a recorded BLOCK (`raw_identifier:<field>:<kind>`). Systems of record should issue short counters or random letters, not hex or numeric ids. PANs and Aadhaar numbers are now detected in every string parameter.
- **Breaking (configuration): connections to Postgres require verified TLS.** `kavach-api`, `kavach-batch` and `kavach-evidence export` / `checkpoints` now connect with `sslmode=verify-full`: TLS, a certificate that chains to a trusted root, and a matching host name. A deployment whose Postgres serves no TLS, or whose database URL names a weaker `sslmode`, no longer starts.
  - **Postgres:** enable TLS (`ssl = on`, `ssl_cert_file`, `ssl_key_file`) with a certificate that names the host in your database URLs. Prefer a DNS name; an IP address works only if the certificate lists it. Use `hostssl` lines in `pg_hba.conf` so the server refuses plaintext too.
  - **Kavach:** if the certificate comes from a private CA, set `--database-ca <pem>` / `KAVACH_DATABASE_CA` (API and batch; also `kavach-evidence export`). Remove any `sslmode=` weaker than `verify-full` from `KAVACH_DATABASE_URL`, `KAVACH_MIGRATION_DATABASE_URL` and `KAVACH_AUDITOR_DATABASE_URL`. `PGSSLMODE` in the environment is ignored.
  - **Pilot compose stack (`deploy/docker-compose.pilot.yml`):** its Postgres now serves TLS only and refuses plaintext. Before `docker compose up`, run `scripts/pilot-db-tls.sh` once: it writes `deploy/pilot-db-tls/` (a certificate for `postgres`, its key, and `ca.pem`, which Kavach verifies with; the CA key is not kept). With your own PKI, put `server.crt`, `server.key` and your CA as `ca.pem` there instead. An existing pilot database keeps its data; only the server's TLS settings change.
  - **Development:** plaintext needs both `--insecure-dev` (export commands: `--allow-plaintext-database`) and `sslmode=disable` in the URL. `kavach-batch` gains `--insecure-dev` for this. The flag alone downgrades nothing.
- **Breaking (configuration):** the agent data plane now requires a checkpoint signing key. Startup fails without `--checkpoint-keys-dir` (`KAVACH_CHECKPOINT_KEYS_DIR`); the key id defaults to `kavach-checkpoint-1` (`--checkpoint-key-id`).
  - Create it with `kavach-keys generate` in a key directory, as for the other keys.
  - It must not share an id with the mandate, evidence or credential key, or key material with the evidence key.
  - A `dev-` key is accepted only with `--insecure-dev`. Development bundles from `kavach-dev generate` already include `dev-checkpoint-1` and its settings; regenerate older bundles.
  - Deployments that do not enable the agent data plane are unaffected.

- The `kavach-evidence` binary moved to the new `kavach-evidence-cli` crate. Its name and its `verify` command are unchanged; build it with `-p kavach-evidence-cli` instead of `-p kavach-evidence`.
- The API refuses to start if its mandate, evidence, checkpoint or credential key id starts with `export-` (or `dev-export-`): those ids are reserved for evidence export keys.
- The evidence commit makes fewer database round trips: 6 instead of 9 for a recorded allow, 3 instead of 5 while it holds the partition lock. Same transaction, lock order and durability.
- Bearer tokens (API callers and agents) are checked against keys decoded once per JWKS load or refresh, rather than on every request. Acceptance rules are unchanged.

### Added

- **Agent-only mode (Phase 0).** `--agent-only` serves the agent surfaces and the operator surface of the agent path, and none of the credit track (evaluate, packs, models, decision events, retention, incidents, batch, the console, the gRPC evaluate service, and credit change requests). It is for hosted builds and refuses to start without the agent surfaces. The *Network isolation* job's stack runs with it. It removes the way to reach the credit track, not the code (the tables stay, and are not tenant-keyed: ADR-014).
- **Alert rules and a dashboard (Phase 0).** `deploy/monitoring/` ships Prometheus alert rules (checkpoint stall and lag, skipped checkpoints, a revocation without its evidence record, a stopped reconciler, outcome write failures, a credential id conflict, unknown outcomes, a slow commit stage, service down, and more) and a Grafana dashboard. The thresholds are starting points. A test fails if a rule or panel names a metric the API does not register.
- **Orderly stop (Phase 0).** On SIGTERM or Ctrl-C `kavach-api` stops accepting connections, lets requests in flight finish, waits for every gateway call that has started (up to `--shutdown-grace-seconds`, default 30), writes a final checkpoint and exits 0. If a listener or a call has not finished by the deadline it logs `ALERT shutdown was not clean` and exits 1. `docker-compose.pilot.yml` gets `stop_grace_period: 45s`. Not built: a readiness drain before the stop.
- **`kavach simulate`: payments and disputes (R1c-3, ADR-012).** A scenario may list system-of-record `events:` (`loan.paid`, `loan.disputed`, `loan.dpd30` for a new default), each for the first borrowers whose messages are delivered. The oracle refuses every call under a mandate issued at or before a borrower's payment or dispute, from the event on (from the scenario alone). Reconciliation checks that each event revoked exactly the mandates the run held, that the evidence holds one signed revocation record per event naming them, and, from the provider's inbox, that nothing was delivered under a revoked mandate after its event. New built-ins `payment-stops-contact` and `dispute-stops-contact`; `mixed-week` gains a payment. Revocation is no longer listed as not covered.
- **Attack catalog version 4 (R1c-2, ADR-012 §8): 30 attacks.** Eight revocation attacks against a borrower kept for them (`ref:borrower:B-ATTACK`): forged, stale, future-dated, unknown type, another tenant, wrong loan, reaching forward, and replayed. Each is judged on the reply and on ground truth: the attack mandate must still authorise, and a refused event must leave no revocation record in the evidence chain (an accepted event that should have been refused is a breach). They run in process (memory and Postgres, also either side of midnight IST) and in `kavach attack`; a project without the attack borrower makes them inconclusive (exit 2, fix `kavach init --force`), never a pass. A test breaks each defence in turn and shows its attack judged `succeeded`.
- **`GET /v1/agent-revocations/{system}/{event_id}`:** the evidence record of a revocation by event, for `read_evidence` holders, rate limited and audited before it is returned, like `GET /v1/agent-decisions/{record_id}`.
- **`kavach sor event --type loan.paid|loan.disputed` (R1c-1, ADR-012).** Sends a signed payment or dispute for a borrower's loan, dated now on the stack's clock: every mandate issued for the loan up to now is revoked, with its delegations, and the command prints the revoked ids. `loan.dpd30` (the default) assigns, as before. There is no option to backdate an event.
- **Revocations are evidence (R1b-2, ADR-012 §7).** Every revocation by a system-of-record event is a signed `mandate_revocation` record in the agent evidence chain, between the decisions: the event (system, id, type, content hash, time), the revoked mandates, `revoked_at` and `recorded_at`. The loan is named only by a keyed pseudonym. The request that revokes writes it; if it cannot, a background reconciler writes it, once per event, and `kavach_revocation_records_missing` with an `ALERT` log line reports any still missing. Chain verification accepts both kinds and refuses any kind it does not know. Migration 016 adds an index for the reconciler.
- **Revocation by system-of-record event (ADR-012, R1a).** A signed `loan.paid` or `loan.disputed` event on `POST /v1/sor/events` revokes every active mandate issued about that loan at or before the event, and every mandate delegated from them; the reply lists them (`revoked`). The event must come from a registered system-of-record issuer, verify, be fresh and pass the replay guard. A retry of the same event gets the stored result (`replayed: true`); the same event id with different content is refused (409). Each revocation is kept (append-only, migration 014) and audited.
- **The gateway re-checks the mandate just before minting a credential.** A mandate revoked between the decision and the send ends the call `not_executed` (`mandate_revoked`): no credential, nothing sent.
- `kavach simulate` S3: every run reconciles three records, its own ledger, Kavach's evidence bundle and the provider's inbox. The inbox is the one record Kavach does not write, so it gives the provider's own proof that each allowed message arrived exactly once (never twice), that nothing blocked or refused arrived, and that each message went to its borrower's own destination. Any finding fails the run. Built-in scenarios name the SECURITY_PROPERTIES.md rows they exercise (`covers:`), and a test fails if a row is renamed or removed.
- `kavach simulate` S2:
  - **Adversarial agent:** makes the attack catalog's tool-call attacks (raw identifiers, another borrower, forged mandate, unregistered tools and values), on borrowers kept for it.
  - **Retries:** agents can send the same request again after an unknown outcome (`retry_rate`).
  - **Provider failures:** the first borrowers can be given a destination where the provider refuses (422), errs (500) or loses the response (`provider_failures`).
  - **Oracle:** now judges the registry, plain references, the mandate's subject, forward-once retries (409 `in_flight` after an unknown outcome) and provider outcomes (a 5xx is unknown).
  - **Six new built-in scenarios**, including `mixed-week`.
- `kavach simulate` (pre-alpha, S1): synthetic agents over simulated days against a throwaway dev stack, judged by an oracle that shares nothing with the agents. Each agent has its own identity and seeded behaviour from the scenario file. Four built-in scenarios: `normal-day`, `after-hours`, `fourth-contact`, `two-agents-one-borrower` (the daily cap holds across two agents' own mandates). The stack's evidence is exported as it stops and verified. Reports list what is not covered first. Exit 0 as expected, 1 not, 2 inconclusive. New crate `kavach-sim`; the devkit can now write a project for any set of agents and borrowers, and `kavach init`'s output is unchanged. See `docs/SIMULATE.md`.

Pull requests that change the workflow, and manual runs, are dry runs. A `v<version>` tag creates a draft pre-release, never a published one. The workspace version is now `0.1.0-alpha.1`. Nothing is published until the name is cleared.

It works with the memory store, so no Postgres is needed. A killed stack writes nothing, and the bundle is signed with dev keys, so it verifies only as a development bundle.

Verification shows what is **not** protected first; exit 0 verified, 2 not fully protected, 1 failed. Same code as `kavach-evidence`.

Tests hold it to the server: every response in the API integration tests is validated against it, a drift test compares its routes, methods and problem codes with the code, and CI lints it with a pinned Redocly CLI. Problem `type` URIs are relative and not meant to be dereferenced yet. The API does not serve the file, and gRPC is not covered.

  - **Clock:** both need a fixed development clock. Without one they are reported as skipped, never passed.
  - **Setup:** reported separately and not judged. Ground truth counts only each attack's judged window.
  - **No more inconclusive under `--clock`:** with a fixed clock, `kavach attack` moves it into contact hours instead of returning inconclusive.

- `kavach attack` (CLI milestone C4) runs the attack catalog against the running dev stack. The catalog (`kavach-attacks`, version 1, 18 attacks) is shared with the acceptance suite, so the CLI runs exactly what CI runs.
  - **The attacks:** raw identifiers, another borrower, a forged mandate, another agent's token, a replayed SoR event, policy limits, request shape, authentication (none, operator, principal header, tampered, unsigned), and the provider without a credential.
  - **Judged on ground truth:** a minted credential or a delivered message means the attack succeeded, whatever the reply said.
  - **`--list`** shows the scope, with each attack's `SECURITY_PROPERTIES.md` and `BYPASS_INVENTORY.md` rows.
  - **Safety:** loopback and dev keys only, rate-limited, never aiming for an allow, request ids prefixed `attack-`.

  - **The 20× acceptance gate** now runs it, and the in-process catalog test, every night.
  - `dev up` serves the mock provider's inbox on a fifth loopback listener (`[listen] inspect`, default 127.0.0.1:8444).
- CLI output prints known digest fields whole (`input_digest`, and the Cedar and registry digests in `why`). Before, the number rule masked any digest that happened to contain ten digits in a row. The exemption is by field, not by pattern: the output layer marks those fields with a per-process nonce that input cannot forge, and only when the value is a well-formed digest. The same hex anywhere else, a malformed value in a digest field, and a phone number inside hex are all still masked. The shared (log) redaction rules are unchanged.
- `kavach why <evidence-id>` for evaluate (credit) decisions (CLI milestone C3c). It shows both decisions and the governance mode (in shadow mode, a PASS return that hides a would-be BLOCK is called out), the reasons, the pack and model versions, and the input only as its digest. This evidence is hash-chained but not signed, so the output says "hash matches the content; not signed, so this does not prove the record wasn't rewritten", never "verified". `--export <file>` checks the whole chain of a decision event export before showing anything. There are no counterfactuals for credit decisions. New operator endpoint `GET /v1/decision-events/{evidence_id}`: `read_evidence` (admins), rate-limited, every read audited, and a tombstoned event redacted as export views show it.
- Counterfactuals in `kavach authorize` (CLI milestone C3b). For a call blocked by exactly one business constraint (contact window, daily cap, channel, waiver ceiling), it says what single change would pass and gives the bound, labelled "what-if under current policies": "at 08:00 IST tomorrow", "after the daily cap resets (08:00 IST tomorrow), contacts < 3", "channel ∈ {whatsapp}", "waiver_bps ≤ 1000". Candidates come from the mandate's window, cap, channels and ceiling, each confirmed by one real re-run of the authorization core. Two failing business constraints get "no single change passes", and safety blocks (raw identifiers, mandate, subject, agent, trusted time) get no suggestions at all. They exist only in the offline CLI: the agent API returns decisions and reasons only, and a test pins that. `kavach why` on a business block prints the `kavach authorize` command to explore it, with placeholders only.
- `kavach why <record-id>` (CLI milestone C3a) explains an agent decision: its reason codes in words with the usual fix, the mandate and chain, trusted time, policy and registry digests and the outcome. The subject is shown only as its pseudonym. It checks the record's hash and signature against local trusted keys ("record signature verified", "against dev keys" in development) and says that one record proves nothing about the chain. `--bundle <dir>` verifies an evidence bundle offline first and explains the record from it. New operator endpoint `GET /v1/agent-decisions/{record_id}`: Cedar action `read_evidence` (admins), rate-limited, and every read audited (who, which record, found or not); a read that cannot be audited is refused. A reason catalog (`kavach_domain::reasons`) explains every code the agent policies, gateway, registry and pack can emit; a test fails if one is missing.
- `kavach policy test [PATH]` (CLI milestone C2c) runs YAML policy test suites (format version 1, pre-alpha) from `policy-tests/`, which `kavach init` now creates with starter suites for collections and credit underwriting. `tool_call` cases are decided offline over a real in-memory mandate, which can be for another borrower or delegated through the real delegation rules. `evaluate` cases run against the project's pack and model. Unknown keys fail the file, and every case must assert a `decision` (with exact `reasons` or `reasons_include`) or `refused` (optionally with a stable code). The agent policies tested are the bundled ones, which the output says. Tool registry refusals now carry stable codes (`ToolRegistry::check`); `extract` is the same check without the code.
- `kavach sor event` and `kavach call <tool>` (CLI milestone C2b): the live path, through the running `kavach dev up`. `sor event` sends a signed system-of-record event stamped on the stack's clock and prints the mandate id. `call` goes through the gateway with the agent's dev token and prints the decision, record id and outcome. It needs `--mandate <id>` or `--issue-mandate`, which sends the event first and says so: a mandate is never issued without a mention. Both are recorded by the stack and use up contact caps; `kavach authorize` does neither. `dev up` writes `.kavach/run.json` (owner-only: process id, addresses, clock offset; no tokens) and removes it on Ctrl-C or SIGTERM. CLI output keeps canonical UUIDs and RFC 3339 timestamps intact; everything else still goes through the shared redaction.
- `kavach authorize <tool>` (CLI milestone C2a): what the gateway would decide for a tool call, offline. It runs the same authorization core in pre-check mode, in process, over a mandate issued in memory from a synthetic system-of-record event and a store that records nothing (`WhatIfStore`). `--at HH:MM`, `--contacts-today N`, `--param NAME=VALUE`, `--agent` and `--subject` vary the question. Required parameters left out get defaults, which the output lists. It exits 0 if the call would be allowed, 1 if not, and 64 for a request the gateway would refuse as malformed.
- The `kavach` developer command line (`crates/kavach-cli`, CLI milestone C1): `kavach init` creates a dev project (`kavach.toml`, plus a git-ignored `.kavach/` bundle of `dev-` keys, tokens and fixtures); `kavach doctor` checks the bundle, key-file permissions, token expiry, loopback ports, disk, database, clock sync and IST contact hours, and says what to fix; `kavach dev up` runs Kavach and the mock provider in one process on loopback (`--at HH:MM` starts the clock at an IST time). Every command takes `--json` (envelope schema `kavach.cli/v1`). Exit codes are stable: 0 ok, 1 failed, 2 warnings, 64 usage. Colour only on a terminal and never with `NO_COLOR`. Every line printed is redacted. No telemetry.
- Key rotation with an overlap (KMS milestone, K3): `previous_mandate_keys` in the mandate configuration lists earlier mandate keys, trusted to verify the mandates they signed until those expire and never used to sign (the current key, by id or material, and duplicates are refused). `docs/KEY_RUNBOOK.md` covers creating, distributing, rotating and retiring every key, and what to do when one is compromised.
- Limits on trusted keys in `kavach-evidence verify-bundle`: each key in the trusted keys file may carry `valid_until_seq` (anchored to a checkpoint kept before a compromise: anything the key signed for a later record is refused unless a kept checkpoint covers it) and `not_before`/`not_after` (time only; a key thief can backdate). Applied to records, outcomes, checkpoints and manifests; a violation fails verification.
- `kavach-evidence export` can sign with an export key held in an HSM: `--key-id export-…` with `--hsm-module`, `--hsm-token-label` and an owner-only `--hsm-pin-file`, instead of `--key-dir`. The key must have been generated in the HSM; only an `export-` key is accepted, checked before the HSM is touched.
- Signing keys in an HSM, per role (KMS milestone, K2): `--hsm-keys mandate,evidence,checkpoint,credential` with `--hsm-module`, `--hsm-token-label` and an owner-only `--hsm-pin-file`. Listed roles sign through the PKCS#11 provider; the others keep their key files. Keys must have been generated in the HSM outside `--insecure-dev`, the key-separation checks cover HSM keys, an HSM signing failure fails closed, and `/v1/runtime` reports `hsm.roles` and `hsm.healthy`.
- Fuzz target `cel_policy`: CEL rules through pack loading and evaluation. A crash is always fixed; a hang becomes a tighter load limit or a documented gap.
- `kavach-keys-pkcs11` (KMS milestone, K1): a PKCS#11 key provider for Ed25519 signing keys held in an HSM. It refuses keys that could have been imported or read out (sensitive, always sensitive, not extractable, never extractable), proves each public key at startup, pools sessions and logs in again after an HSM restart, and fails closed otherwise. Tested against SoftHSM2 in CI. Not wired into the API yet (K2).

### Not yet

- Truncation and rewrites are detected only by verifying an export against a checkpoint the operator copied off-host; the live database is not checked continuously, and nothing is anchored outside the operator's own storage.
- A deleted outcome row is detected only against an earlier signed bundle that contains it.

### Fixed

- **A gateway call no longer dies with its client.** The call used to run inside the request handler, so a client that disconnected between "sent" and "outcome recorded" cancelled it: the allow was left without an outcome (`outcome_missing`) and its retry was refused as in flight. The call now runs in a task of its own, counted while it runs, and completes whether or not the client is still there. `kavach dev up` also waits for calls in flight before its final checkpoint and export.
- `kavach attack` can run again on the same stack: request and event ids carry a per-run suffix (a second run used to be refused with 409 for reusing them), and on a fixed clock a run moves to a fresh day when an earlier run used the day's contacts.

- Request bodies with free-form JSON (`/v1/evaluate`, `/v1/authorize`, `/v1/tools/{tool}`, change proposals) refuse the key `$serde_json::private::RawValue` anywhere, escaped forms included (400). serde_json would otherwise read its value as a string of JSON, so Kavach would act on a different structure than other parsers see in the same bytes.
- A CEL rule that makes the third-party CEL parser or interpreter panic no longer crashes Kavach: the pack is refused at load (`CelCompile`), and a panic during evaluation is an evaluation error, recorded as a BLOCK. A trailing `&&` was enough to make the parser panic. Found by the `cel_policy` fuzz target.
- Canonical JSON (everything signed or hashed as evidence) refuses objects with the key `$serde_json::private::RawValue`. serde_json, with the `raw_value` feature that axum and sqlx switch on, parses an object whose first key is that token as a string of JSON, so its canonical form (which sorts `$` first) would not parse back to itself. Found by the `jcs_differential` fuzz target. No signed type can carry such a key today.
- Bearer tokens (API callers and agents) whose JOSE header is not a UTF-8 JSON object are refused (RFC 7515 §4). Before, the JWT library skipped unknown header members without checking their bytes. Found by the `agent_token` fuzz target; only a key the identity provider holds could sign such a token.
- HMAC v2: the timestamp skew check no longer overflows on an extreme `X-Kavach-Timestamp`. Builds with overflow checks panicked before the signature was checked; release builds wrapped, so one timestamp value passed the skew check (the signature was still required).
