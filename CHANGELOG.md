# Changelog

Notable changes to Kavach. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Kavach is pre-alpha: there are no releases yet, and anything may change before v0.1.

## [Unreleased]

### Changed

- **Breaking for anyone recomputing evaluate evidence hashes: `DecisionEvent` schema 1.1.0 hashes `decision_time` and `evaluated_at` at microsecond precision.** They used to be hashed with nanoseconds, but Postgres keeps microseconds, so an event read back from the database did not hash to its stored hash and could not be re-checked. Both stores now truncate the two timestamps before hashing, so what is stored is what was hashed.
  - **The hash rule is unchanged** (same fields, same canonical order); the canonical form of the two values changed, hence the minor version.
  - **Records at 1.1.0 or later must re-verify exactly.**
  - **Pre-1.1.0 records** still verify wherever their nanoseconds survive, and mixed chains verify; nothing is re-fingerprinted. Read back from Postgres, a pre-1.1.0 record that fails only as lost precision explains is reported as **legacy: cannot be re-checked**. `kavach-evidence verify` exits 2 with a warning: never "verified", and not called tampered.
  - **No downgrade:** a pre-1.1.0 record after a 1.1.0 one is refused.
  - **Pilots should re-baseline:** export, then start a fresh chain.
  - **Independent verifiers** must truncate the two timestamps first.
  - See `docs/DECISION_EVENT_COMPAT.md`.
- **Breaking (evaluate API): a consent whose purpose differs from the request's is now a recorded BLOCK with `CONSENT_MISMATCH`, as ADR-001 §7 step 4 and §9 specify.** Until now, `POST /v1/evaluate`, gRPC and batch refused such a request as a validation error (400 / `INVALID_ARGUMENT` / a `validation_error` row) before any decision, and wrote no evidence. Now it gets a decision and an evidence row. In shadow mode the returned decision is PASS, with `policy_decision` BLOCK. The engine applies the check itself, so a pack without a consent rule still blocks a mismatch. Callers that treated the 400 as "consent refused" should read the BLOCK instead.
- **Breaking (evaluate API): a request with no `consent` object is also a recorded BLOCK with `CONSENT_MISMATCH`** (the pack's code for an absent consent), because ADR-001 §9 makes presence an engine check. `consent` is now optional in the request: HTTP and batch used to refuse a missing field as malformed, and gRPC refused it with `missing consent`. A consent object that is present but malformed, for example without `timestamp`, is still refused. The decision's evidence holds `input_digest` only, never the raw input.
- Log redaction leaves canonical UUIDs and full RFC 3339 timestamps whole. The number rule masked fractional seconds and about one UUID in five, so record and mandate ids in the logs couldn't be searched. The match is strict: a lowercase versioned UUID with at least one letter, and a timestamp with `T`, a zone, a 19xx/20xx year, no word character on either side, and a value that parses. Phone, Aadhaar and PAN numbers beside or glued to such spans are still masked.
- **Policy engine: the CEL implementation moved from `cel-interpreter` 0.10 to `cel` 0.14.5** (the same project under its current crate name). It returns syntax errors where the old parser panicked (an incomplete expression such as `a &&`). **Treat this as a policy change:** a change in the engine's semantics changes what a signed pack decides even when the pack's bytes do not. Every golden fixture and scenario test gives the same decisions as before; run your own pack tests before upgrading. Kavach's own guards stay: panics in the CEL crates are contained, packs are bounded at load, and evaluation has a wall-clock timeout.
- **Agents: references are held to a published format.** A reference-only parameter (`ref:<type>:<id>`) may hold at most 8 digits in total, however spread, and nothing that reads as a PAN (ADR-004 §7). Anything else is a recorded BLOCK (`raw_identifier:<field>:<kind>`). Systems of record should issue short counters or random letters, not hex or numeric ids. PANs and Aadhaar numbers are now detected in every string parameter.
- **Breaking (configuration): connections to Postgres require verified TLS.** `kavach-api`, `kavach-batch` and `kavach-evidence export` / `checkpoints` now connect with `sslmode=verify-full`: TLS, a certificate that chains to a trusted root, and a matching host name. A deployment whose Postgres serves no TLS, or whose database URL names a weaker `sslmode`, no longer starts.
  - **Postgres:** enable TLS (`ssl = on`, `ssl_cert_file`, `ssl_key_file`) with a certificate that names the host in your database URLs. Prefer a DNS name; an IP address works only if the certificate lists it. Use `hostssl` lines in `pg_hba.conf` so the server refuses plaintext too.
  - **Kavach:** if the certificate comes from a private CA, set `--database-ca <pem>` / `KAVACH_DATABASE_CA` (API and batch; also `kavach-evidence export`). Remove any `sslmode=` weaker than `verify-full` from `KAVACH_DATABASE_URL`, `KAVACH_MIGRATION_DATABASE_URL` and `KAVACH_AUDITOR_DATABASE_URL`. `PGSSLMODE` in the environment is ignored.
  - **Pilot compose stack (`deploy/docker-compose.pilot.yml`):** its Postgres now serves TLS only and refuses plaintext. Before `docker compose up`, run `scripts/pilot-db-tls.sh` once: it writes `deploy/pilot-db-tls/` (a certificate for `postgres`, its key, and `ca.pem`, which Kavach verifies with; the CA key is not kept). With your own PKI, put `server.crt`, `server.key` and your CA as `ca.pem` there instead. An existing pilot database keeps its data; only the server's TLS settings change.
  - **Development:** plaintext needs both `--insecure-dev` (export commands: `--allow-plaintext-database`) and `sslmode=disable` in the URL. `kavach-batch` gains `--insecure-dev` for this. The flag alone downgrades nothing.
- **Breaking (configuration):** the agent data plane now requires a checkpoint signing key. Startup fails without `--checkpoint-keys-dir` (`KAVACH_CHECKPOINT_KEYS_DIR`); the key id defaults to `kavach-checkpoint-1` (`--checkpoint-key-id`).
  - Create it with `kavach-keys generate` in a key directory, as for the other keys.
  - It must not share an id with the mandate, evidence or credential key, or key material with the evidence key.
  - A `dev-` key is accepted only with `--insecure-dev`. Development bundles from `kavach-dev generate` already include `dev-checkpoint-1` and its settings; regenerate older bundles.
  - Deployments that do not enable the agent data plane are unaffected.

- The `kavach-evidence` binary moved to the new `kavach-evidence-cli` crate. Its name and its `verify` command are unchanged; build it with `-p kavach-evidence-cli` instead of `-p kavach-evidence`.
- The API refuses to start if its mandate, evidence, checkpoint or credential key id starts with `export-` (or `dev-export-`): those ids are reserved for evidence export keys.
- The evidence commit makes fewer database round trips: 6 instead of 9 for a recorded allow, 3 instead of 5 while it holds the partition lock. Same transaction, lock order and durability.
- Bearer tokens (API callers and agents) are checked against keys decoded once per JWKS load or refresh, rather than on every request. Acceptance rules are unchanged.

### Added

- CLI output prints known digest fields whole (`input_digest`, and the Cedar and registry digests in `why`). Before, the number rule masked any digest that happened to contain ten digits in a row. The exemption is by field, not by pattern: the output layer marks those fields with a per-process nonce that input cannot forge, and only when the value is a well-formed digest. The same hex anywhere else, a malformed value in a digest field, and a phone number inside hex are all still masked. The shared (log) redaction rules are unchanged.
- `kavach why <evidence-id>` for evaluate (credit) decisions (CLI milestone C3c). It shows both decisions and the governance mode (in shadow mode, a PASS return that hides a would-be BLOCK is called out), the reasons, the pack and model versions, and the input only as its digest. This evidence is hash-chained but not signed, so the output says "hash matches the content; not signed, so this does not prove the record wasn't rewritten", never "verified". `--export <file>` checks the whole chain of a decision event export before showing anything. There are no counterfactuals for credit decisions. New operator endpoint `GET /v1/decision-events/{evidence_id}`: `read_evidence` (admins), rate-limited, every read audited, and a tombstoned event redacted as export views show it.
- Counterfactuals in `kavach authorize` (CLI milestone C3b). For a call blocked by exactly one business constraint (contact window, daily cap, channel, waiver ceiling), it says what single change would pass and gives the bound, labelled "what-if under current policies": "at 08:00 IST tomorrow", "after the daily cap resets (08:00 IST tomorrow), contacts < 3", "channel ∈ {whatsapp}", "waiver_bps ≤ 1000". Candidates come from the mandate's window, cap, channels and ceiling, each confirmed by one real re-run of the authorization core. Two failing business constraints get "no single change passes", and safety blocks (raw identifiers, mandate, subject, agent, trusted time) get no suggestions at all. They exist only in the offline CLI: the agent API returns decisions and reasons only, and a test pins that. `kavach why` on a business block prints the `kavach authorize` command to explore it, with placeholders only.
- `kavach why <record-id>` (CLI milestone C3a) explains an agent decision: its reason codes in words with the usual fix, the mandate and chain, trusted time, policy and registry digests and the outcome. The subject is shown only as its pseudonym. It checks the record's hash and signature against local trusted keys ("record signature verified", "against dev keys" in development) and says that one record proves nothing about the chain. `--bundle <dir>` verifies an evidence bundle offline first and explains the record from it. New operator endpoint `GET /v1/agent-decisions/{record_id}`: Cedar action `read_evidence` (admins), rate-limited, and every read audited (who, which record, found or not); a read that cannot be audited is refused. A reason catalog (`kavach_domain::reasons`) explains every code the agent policies, gateway, registry and pack can emit; a test fails if one is missing.
- `kavach policy test [PATH]` (CLI milestone C2c) runs YAML policy test suites (format version 1, pre-alpha) from `policy-tests/`, which `kavach init` now creates with starter suites for collections and credit underwriting. `tool_call` cases are decided offline over a real in-memory mandate, which can be for another borrower or delegated through the real delegation rules. `evaluate` cases run against the project's pack and model. Unknown keys fail the file, and every case must assert a `decision` (with exact `reasons` or `reasons_include`) or `refused` (optionally with a stable code). The agent policies tested are the bundled ones, which the output says. Tool registry refusals now carry stable codes (`ToolRegistry::check`); `extract` is the same check without the code.
- `kavach sor event` and `kavach call <tool>` (CLI milestone C2b): the live path, through the running `kavach dev up`. `sor event` sends a signed system-of-record event stamped on the stack's clock and prints the mandate id. `call` goes through the gateway with the agent's dev token and prints the decision, record id and outcome. It needs `--mandate <id>` or `--issue-mandate`, which sends the event first and says so: a mandate is never issued without a mention. Both are recorded by the stack and use up contact caps; `kavach authorize` does neither. `dev up` writes `.kavach/run.json` (owner-only: process id, addresses, clock offset; no tokens) and removes it on Ctrl-C or SIGTERM. CLI output keeps canonical UUIDs and RFC 3339 timestamps intact; everything else still goes through the shared redaction.
- `kavach authorize <tool>` (CLI milestone C2a): what the gateway would decide for a tool call, offline. It runs the same authorization core in pre-check mode, in process, over a mandate issued in memory from a synthetic system-of-record event and a store that records nothing (`WhatIfStore`). `--at HH:MM`, `--contacts-today N`, `--param NAME=VALUE`, `--agent` and `--subject` vary the question. Required parameters left out get defaults, which the output lists. It exits 0 if the call would be allowed, 1 if not, and 64 for a request the gateway would refuse as malformed.
- The `kavach` developer command line (`crates/kavach-cli`, CLI milestone C1): `kavach init` creates a dev project (`kavach.toml`, plus a git-ignored `.kavach/` bundle of `dev-` keys, tokens and fixtures); `kavach doctor` checks the bundle, key-file permissions, token expiry, loopback ports, disk, database, clock sync and IST contact hours, and says what to fix; `kavach dev up` runs Kavach and the mock provider in one process on loopback (`--at HH:MM` starts the clock at an IST time). Every command takes `--json` (envelope schema `kavach.cli/v1`). Exit codes are stable: 0 ok, 1 failed, 2 warnings, 64 usage. Colour only on a terminal and never with `NO_COLOR`. Every line printed is redacted. No telemetry.
- Key rotation with an overlap (KMS milestone, K3): `previous_mandate_keys` in the mandate configuration lists earlier mandate keys, trusted to verify the mandates they signed until those expire and never used to sign (the current key, by id or material, and duplicates are refused). `docs/KEY_RUNBOOK.md` covers creating, distributing, rotating and retiring every key, and what to do when one is compromised.
- Limits on trusted keys in `kavach-evidence verify-bundle`: each key in the trusted keys file may carry `valid_until_seq` (anchored to a checkpoint kept before a compromise: anything the key signed for a later record is refused unless a kept checkpoint covers it) and `not_before`/`not_after` (time only; a key thief can backdate). Applied to records, outcomes, checkpoints and manifests; a violation fails verification.
- `kavach-evidence export` can sign with an export key held in an HSM: `--key-id export-…` with `--hsm-module`, `--hsm-token-label` and an owner-only `--hsm-pin-file`, instead of `--key-dir`. The key must have been generated in the HSM; only an `export-` key is accepted, checked before the HSM is touched.
- Signing keys in an HSM, per role (KMS milestone, K2): `--hsm-keys mandate,evidence,checkpoint,credential` with `--hsm-module`, `--hsm-token-label` and an owner-only `--hsm-pin-file`. Listed roles sign through the PKCS#11 provider; the others keep their key files. Keys must have been generated in the HSM outside `--insecure-dev`, the key-separation checks cover HSM keys, an HSM signing failure fails closed, and `/v1/runtime` reports `hsm.roles` and `hsm.healthy`.
- Fuzz target `cel_policy`: CEL rules through pack loading and evaluation. A crash is always fixed; a hang becomes a tighter load limit or a documented gap.
- `kavach-keys-pkcs11` (KMS milestone, K1): a PKCS#11 key provider for Ed25519 signing keys held in an HSM. It refuses keys that could have been imported or read out (sensitive, always sensitive, not extractable, never extractable), proves each public key at startup, pools sessions and logs in again after an HSM restart, and fails closed otherwise. Tested against SoftHSM2 in CI. Not wired into the API yet (K2).
- Fuzz target `bundle_verify`: evidence bundles through the whole `verify-bundle` path, from byte edits to the checked-in signed bundle and from arbitrary files. A bundle that verifies as signed must be byte-identical to the original.
- Fuzz target `credential_open`: resource credentials as a provider opens them, from any string, from fuzzed claims that are signed and encrypted, and from byte edits to the checked-in credential vector.
- Fuzz targets for agent tool parameters (no raw identifier in a reference-only field), HMAC v2 headers (fixed clock, fresh nonce store) and canonical JSON (a differential against a reference serialiser), plus RFC 8785 vectors that CI checks independently with the `canonicalize` package.
- `docs/BYPASS_INVENTORY.md`: every known way around a guarantee, who can use it and how it would be noticed. Every guarantee in `docs/SECURITY_PROPERTIES.md` now carries a status (Enforced, Conditional, Reference, Dev stack).
- Fuzzing (`fuzz/`, cargo-fuzz): targets for JWS of every Kavach type, signed and unsigned, system-of-record events through mandate issuance, and agent access tokens, each with invariants beyond "no crash". A nightly *Fuzz* workflow with memory, time and size limits per target, not a required check.
- `kavach-bench` scenario `authorize`: the decision alone, in process, for the NFR-2 `authorize` p99 target. It leaves out HTTP and token verification, which `precheck` includes.
- `kavach_gateway_stage_seconds{stage}`: a histogram of each gateway call's stages (decide, commit, resolve, credential, forward, outcome), and a per-stage breakdown in the benchmark report.
- `--database-pool-size` / `KAVACH_DATABASE_POOL_SIZE` for the API's runtime Postgres pool (default 5, as before).
- `kavach-bench`, a benchmark harness for the gateway path (delivered, blocked, pre-check and hot-subject calls at fixed concurrency; storage micro-benchmarks for the evidence commit and the outcome write with and without an extra lock; several pool sizes per run), and an on-demand *Benchmarks* workflow that records trends with and without database TLS. How figures may be quoted: `docs/PERFORMANCE.md`. No published numbers yet.

- Evidence bundle format v1 (manifest, writer, test vector), the export key rules and the read-only `kavach_auditor` database role (migration 013).
- `kavach-evidence export` writes the agent chain (or a segment after a checkpoint) as a signed bundle from one read-only snapshot, and `kavach-evidence checkpoints` prints checkpoints to copy off-host. Both refuse a database role that can write evidence.
- Development bundles (`kavach-dev generate`) include an export key, `auditor/dev-export-1`, and the public keys for verifying a bundle of that stack, `auditor/trusted-keys.json`.
- `kavach-evidence verify-bundle` checks a bundle offline with keys the operator supplies and, with `--expect-checkpoint`, against a checkpoint kept off-host: a chain cut short or rewritten is detected. It fails closed: exit `1` when the bundle does not verify, exit `2` when it verifies but is not fully protected (`--allow-warnings` accepts that), exit `0` otherwise.

- Signed evidence checkpoints for the agent chain (ADR-005 §13): a background writer, the `evidence_checkpoints` table (migration 012), `--checkpoint-interval-seconds` and `--checkpoint-stall-seconds`.
- Checkpoint health in `GET /v1/runtime` (`checkpoint_lag_seconds`, `checkpoint_stalled`, `checkpoint_last_seq`, `checkpoint_uncovered_records`) and in the metrics (`kavach_checkpoint_*`, `kavach_checkpoints_*`).
- Checkpoint format v1, with test vectors and a specification in `docs/EVIDENCE_BUNDLE.md`.

### Not yet

- Truncation and rewrites are detected only by verifying an export against a checkpoint the operator copied off-host; the live database is not checked continuously, and nothing is anchored outside the operator's own storage.
- A deleted outcome row is detected only against an earlier signed bundle that contains it.

### Fixed

- Request bodies with free-form JSON (`/v1/evaluate`, `/v1/authorize`, `/v1/tools/{tool}`, change proposals) refuse the key `$serde_json::private::RawValue` anywhere, escaped forms included (400). serde_json would otherwise read its value as a string of JSON, so Kavach would act on a different structure than other parsers see in the same bytes.
- A CEL rule that makes the third-party CEL parser or interpreter panic no longer crashes Kavach: the pack is refused at load (`CelCompile`), and a panic during evaluation is an evaluation error, recorded as a BLOCK. A trailing `&&` was enough to make the parser panic. Found by the `cel_policy` fuzz target.
- Canonical JSON (everything signed or hashed as evidence) refuses objects with the key `$serde_json::private::RawValue`. serde_json, with the `raw_value` feature that axum and sqlx switch on, parses an object whose first key is that token as a string of JSON, so its canonical form (which sorts `$` first) would not parse back to itself. Found by the `jcs_differential` fuzz target. No signed type can carry such a key today.
- Bearer tokens (API callers and agents) whose JOSE header is not a UTF-8 JSON object are refused (RFC 7515 §4). Before, the JWT library skipped unknown header members without checking their bytes. Found by the `agent_token` fuzz target; only a key the identity provider holds could sign such a token.
- HMAC v2: the timestamp skew check no longer overflows on an extreme `X-Kavach-Timestamp`. Builds with overflow checks panicked before the signature was checked; release builds wrapped, so one timestamp value passed the skew check (the signature was still required).
