# Consent and reference stores — pilot plan

**Status:** Accepted on 2026-11-18. The owner approved signed tenant-bound updates, a dedicated local reference-encryption key with decrypt-only previous keys, first-source pinning with strictly newer destination timestamps, and fail-closed contact when a current preference record is missing. Implemented slices include the local contracts, Postgres projections, signed update verifier and writers, atomic consent withdrawal/revocation, encrypted-reference codec/key rotation, ciphertext-only Postgres table, read-only resolver, and separate signed API ingestion routes for consent/preferences and destinations. Live consent reads and current preference enforcement remain pending; mandate issuance and the gateway still use their fixtures.
**Scope:** The next pilot blocker in `AGENTS.md`; PRD D7/FR-8, ADR-004 §5/§7 and ADR-006 §4. Tier 1 remains one tenant per stack (ADR-014). This plan uses local Postgres and file-held keys, with no paid service dependency.

## Current boundary

- `ConsentSource` reads a startup JSON fixture. `ConsentRecord` has a tenant, subject reference, purposes, expiry and active flag. Mandate issuance checks active status, subject, purpose and expiry.
- `ReferenceResolver` reads a startup JSON fixture and accepts synthetic destinations only. The gateway resolves after authorization and never returns the destination to the agent.
- A pilot needs live changes and real destinations. Reading files once at startup cannot enforce a later withdrawal or opt-out. Storing a real destination as plaintext would break the repo's privacy rule.

## Proposed implementation order

1. **Consent contract.** Define the local consent artefact subset and contact preferences without claiming to implement the full ReBIT API. Keep existing fixture fields readable. Add explicit validity start, information types, data date range and status; reject malformed intervals and unknown status values at load. The status used to authorize a mandate is derived from the stored record, never from an agent request.
2. **Persistent consent and preferences.** Add tenant-scoped Postgres records behind `ConsentSource` and a separate channel opt-out lookup. A missing, expired, withdrawn or unreadable required record fails closed. An opt-out blocks contact on that channel. Use immutable change history plus a current-state projection, and test tenant separation and concurrent withdrawal against issuance and execution.
3. **Signed updates.** Accept consent grants, withdrawals and preference changes only from an authenticated, tenant-bound system-of-record source. A withdrawal revokes affected mandates through the existing revocation path. Replayed update IDs are idempotent; conflicting payloads are refused. Fixture loading remains available for local development only.
4. **Encrypted reference vault.** Store tenant/subject/channel indexes separately from AES-256-GCM encrypted destinations. Bind ciphertext to tenant, subject reference, channel, version and key id as authenticated data. Use a dedicated owner-readable local key file initially, with an adapter boundary for HSM/KMS. Reject a missing or unknown key; never log or return plaintext outside the gateway's existing `Destination` type. Keep keys available for live ciphertext during rotation, and document retirement and restore steps.
5. **Gateway wiring.** Select persistent adapters at startup for pilot mode. Resolve only after the existing authorization and current consent/preference checks. Keep fixture adapters limited to explicit development mode. Run memory/Postgres port conformance, fault tests, migration tests and a live withdrawal/opt-out acceptance path before enabling real destinations.

## Approved decisions

1. **Authority for updates (recommended):** signed, tenant-bound system-of-record events; no direct operator edit of consent or destination values.
2. **Reference encryption (recommended):** a dedicated local AES-256-GCM key file and explicit decrypt-only previous keys, following the review-snapshot key rotation pattern. No reuse of the review-snapshot key.
3. **Missing contact preference (recommended):** fail closed for outbound contact until the authoritative source has supplied a current preference record. This is stricter than the current fixture behavior and requires seeding for pilots.

The first code slice added the backward-compatible consent contract and fixture validation. The next slices added the preference lookup contract, Postgres projections, signed update verifier, transactional preference writer, transactional signed consent grant writer, and atomic consent withdrawal/mandate revocation. The eighth slice adds the encrypted-reference envelope and local key rotation primitive. The ninth adds ciphertext-only Postgres persistence and a runtime read-only resolver. The tenth extends the signed update envelope to destinations. The eleventh adds atomic encrypted writes with source pinning and timestamp ordering. The twelfth adds `POST /v1/sor/reference-destinations`, active/previous vault-key startup configuration, and API selection of the signed writer. The thirteenth adds `POST /v1/sor/authority-updates` to select the existing signed consent/preference writers. Neither ingestion route switches live consent reads or gateway resolution. Security claims, migration guidance and acceptance status change with the slice that changes their guarantees.

## Signed update envelope and verification boundary

An update is a canonical Ed25519 JWS with `typ` `kavach-authority-update+jws`. Its payload has `update_id`, `tenant_id`, `system`, `occurred_at`, `nonce` and a `change` tagged as `consent`, `contact_preference`, or `reference_destination` with a `record`. The signer must be registered for that exact tenant and source system in the governed mandate configuration. Signed consent changes require an explicit artefact: active means grant, revoked means withdrawal; expiry is time based. Preference changes carry `allowed` or `opted_out`. Destination updates bind one destination to a tenant, capability reference, and supported channel; they are permissive changes and therefore require trusted, fresh time. Their transient destination value is redacted in debug output and zeroized on drop. It must be encrypted before persistence and must never be logged or returned. The record tenant must match the signed envelope, and subject references must be capabilities.

Grants, preference allows, and destination updates require a trusted clock and the existing SoR freshness window, capped at 60 seconds into the future. Withdrawals and opt-outs may arrive late or during clock uncertainty because they reduce authority. The verifier returns the canonical payload SHA-256 for durable update-ID idempotency. The API selects the consent/preference writers when Postgres is configured and accepts only the consent and preference variants on `/v1/sor/authority-updates`; destination variants use the separately configured encrypted-vault route. These writes do not change the fixture-backed consent reads used by mandate issuance or the gateway's contact decisions.

Migration 034 lets the runtime append to `authority_updates` and insert/update `contact_preference_current`; migration 035 adds runtime insert/update access to `consent_current` and includes the existing mandate and revocation write grants. Migration 036 indexes recorded consent withdrawals for the issuance barrier. `PostgresAuthorityUpdateStore` accepts only a `VerifiedAuthorityUpdate` and commits consent history/current state with matching mandate revocation in one transaction. It locks under the same tenant advisory lock as root issuance and delegation. An exact `(tenant, source, update_id)` retry returns the recorded revoked set; changed payloads are refused. A withdrawal targets active root mandates whose `consent_refs` contain the consent ID, then revokes their active descendants. It also leaves a durable consent-ID barrier so an issuance whose earlier consent read raced with the withdrawal is refused. The revocation row records whether Kavach's clock met the configured sync bound; unsynchronised clocks do not block restrictive withdrawals. A later grant cannot reopen an inactive current consent record. For preferences, the first source pins its system; a late opt-out may supersede an allow, while an allow cannot reopen an opt-out. The API selects these write adapters when Postgres is configured; the Postgres consent and preference read adapters are not yet selected, so issuance and gateway decisions remain fixture-backed.

## Migration and current rollout boundary

Migration 033 adds append-only `authority_updates` history and tenant-scoped `consent_current` and `contact_preference_current` projections. Migration 034 grants preference writes; migration 035 grants consent projection writes and the existing mandate-revocation permissions; migration 036 adds the consent-withdrawal barrier index. Migration 037 adds `reference_destinations`, which stores scope indexes and authenticated ciphertext only. Migration 038 admits destination metadata to append-only update history and adds source-binding columns. The runtime writer encrypts before persistence, stores only metadata and payload digest in history, pins each tenant/reference/channel to its first signed source, and accepts only strictly newer source timestamps. Runtime can update ciphertext/version fields but cannot change the pinned source or delete a destination. Preexisting rows without source metadata are readable but cannot be overwritten by signed updates until reconciled. The SoR API now selects signed consent/preference persistence and, when the vault key is configured, signed destination persistence. Mandate issuance and gateway reads remain fixture-backed until live consent/preference checks are wired.

The encrypted-reference codec is implemented in `kavach-storage`. It stores only an AES-256-GCM envelope, with tenant, subject reference, channel, record version and key id authenticated as associated data. `ReferenceVaultKey` reads 32-byte hex keys from regular owner-only files, encrypts with the active key, and opens ciphertext with explicitly configured previous keys. Migration 037 and the read-only Postgres resolver are implemented. Migration 038 and `PostgresReferenceDestinationStore` add atomic destination writes, idempotent retries, metadata/digest-only history, first-source pinning and strictly newer timestamps. The API selects signed consent/preference writers on Postgres and loads active plus decrypt-only previous vault keys for destination ingestion. Next, select the persistent read sources and enforce current consent/preference at the authorization-to-gateway boundary; no destination may be sent before authorization and current preference checks.
