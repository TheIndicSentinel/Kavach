# Security Properties and Limitations

This document states exactly what Kavach guarantees, what is planned, and what it does **not** protect. It is updated in the same pull request as any change to a guarantee ([PRD](PRD.md) NFR-6). Claims here must never be stronger than the implementation.

**Version:** pre-v0.1 (Decision Governance and the agent data plane implemented).

Every way known to get around these guarantees, and how it would be noticed, is in [BYPASS_INVENTORY.md](BYPASS_INVENTORY.md).

## Status tags

Each guarantee carries one of these:

| Status | Meaning |
|---|---|
| **Enforced** | Holds in every start outside `--insecure-dev`. Kavach refuses to start, or refuses the request, rather than run without it |
| **Conditional** | Holds only when the named option or procedure is in place (the property says which). Without it, the guarantee is absent, not weakened |
| **Reference** | Holds for Kavach's reference components (the fixture resolver, the mock provider). A deployment's own adapter must pass the same conformance suite before it holds there |
| **Dev stack** | Demonstrated on the development stack (development keys, `--insecure-dev`), not on a production configuration |

Properties not yet guaranteed are under *Planned*; known gaps are under *Not guaranteed*.

## Not guaranteed

**Revocation and time (ADR-012, ADR-016):**

- **A payment or dispute event that never arrives.** Kavach acts on the events it receives. If a `loan.paid` is lost, the loan's mandate stays live until it expires (at most the template's `ttl_seconds`, itself capped at 30 days) or an operator stops the agent. Nothing in the transaction design can prevent this. It is **detected**, not prevented, when the lender's list of closed loans is sent to snapshot reconciliation (`kavach reconcile`); nothing runs that on a schedule, so how soon it is found is how often the lender sends the list.
- **Releasing a dispute hold.** There is no release path: a loan with a recorded dispute stays held against new mandates until one is accepted and built (ADR-016, Proposed).
- **The skew margin and the future clamp are provisional.** 30 s (how close in time two events from two clocks may be before the order is treated as unknown) and 300 s (how long a payment dated ahead can hold a record closed) are named constants, not measured from any lender's source system. A genuine new default within 30 s after a payment is refused, or its mandate revoked if it was already issued, by design.
- **A mixed-version upgrade.** The source-time scope, the closure check and the audit-from-row repair hold only when every replica runs the version with migrations 020 to 022. An older replica neither keeps the source time nor enforces the closure, and an older binary cannot start against the migrated database (it refuses migrations it does not know); a rollback drops the three columns first.
- **Issuing while the clock is not synchronised.** Authority is not issued or delegated then (503); nothing is spent and the sender retries. That is a fail-closed behaviour; it is counted (`kavach_sor_events_unavailable_total{kind="issuing"}`, proven by a test) and the alert `KavachSorEventsUnavailable` fires when it keeps rising, but the counter does not say *why* (clock or store), and without an operator watching it still looks like an outage.
- **A revocation applied on an unsynchronised clock** is flagged on its stored row and in the audit entry (`clock_synced`), not in the signed evidence record.
- **Throughput of issuing and revoking.** The closure check and the revocation take the tenant's mandate lock, so they serialise per tenant. A correctness choice, a throughput limit.
- **Evidence for the newest revocation work.** The source-time scope, barrier, dispute hold, audit-from-row, clock gating and the 60 s issuing bound merged while Actions was unavailable; their evidence is a local Postgres run, and the CI log is owed (`docs/SECOND_REVIEW.md`, "Owed CI evidence").

- **Client certificates to Postgres.** Kavach authenticates to Postgres with a role and password over verified TLS. Mutual TLS (a client certificate for the database connection) is not supported or tested; `sslcert`/`sslkey` in a URL are passed to the driver untested.
- **A Postgres server you run that also accepts plaintext.** Kavach never connects in plaintext outside a development mode, but it cannot stop other clients from doing so: require TLS on the server too (`hostssl` in `pg_hba.conf`). The bundled compose stacks do (`deploy/postgres/pg_hba.conf`), and the Network isolation job checks that their Postgres refuses a plaintext client.
- **One evidence chain.** Agent records chain separately from v1 `decision_events` until M2 (ADR-005 §12).
- **Per-subject erasure of agent records.** Subjects are keyed pseudonyms; one subject cannot be crypto-shredded until M2.
- **Chain truncation and full rewrites, without a kept checkpoint.** Whoever holds both the database and the keys can rewrite the agent chain and its checkpoints. This is detected only by verifying an export against a checkpoint that was copied off-host earlier (see the property above); without one, and for records newer than the last kept checkpoint, it is not. The live database is not checked continuously. A deleted outcome row is detected only against an earlier signed bundle that contains it; the rows are not chained (ADR-005 §13, E5).
- **The delegating agent is caller-supplied in the library.** `MandateService::delegate` takes `by_agent` from its caller. No HTTP route exposes delegation yet, so no request can supply it; the delegation API (its own ADR) must derive it from the authenticated agent before one exists. `contacts_today` is no longer caller-supplied: the gateway reads it from the stored daily counters.
- **Contact-hours source.** The 08:00–19:00 IST floor follows RBI directions on recovery agents as summarised in our research; it awaits compliance sign-off and is guidance, not legal advice.
- **Delivery time on asynchronous channels.** Authorising a WhatsApp or SMS contact at 18:59 does not guarantee delivery before 19:00. Kavach bounds what it controls: no send starts after the record's `send_by`, and no credential outlives it (see *Gateway*). When the provider delivers is the provider's.
- **Resources not routed through Kavach.** The agent guarantees apply only to resources brokered by the Kavach gateway and credential broker, deployed with the network isolation in ADR-007.
- **`--insecure-dev` mode.** Every request is allowed; for local development only.
- **Two identities for one person.** Distinct approval assumes the IdP gives each person one identity and assigns `change-approvers` only to people; two accounts for one person pass as two principals. That is an IdP and process control.
- **Proposer revocation during a pending request.** The proposer's rights are checked at proposal; a group removed in the IdP afterwards is not re-checked (their token is gone). Pending requests expire (default 24 h), and an approver can reject.
- **Break-glass.** Every governance change needs two people; with a single admin available nothing can change, including urgent erasure.
- **Change-request and audit tables against a database administrator.** The runtime role cannot change them, but the owner role or a superuser can (single-role development deployments give the application owner rights). Signed governance events on the chain are planned (P1, ADR-005).
- **Evidence integrity against a database writer.** The v1 `decision_events` chain is unkeyed and not externally anchored, so someone with write access to Postgres can rewrite and re-hash the whole chain. The runtime role is INSERT-only on it; `kavach_credit_auditor` is SELECT-only on decision events, chain heads and checkpoints. When agent surfaces are configured, the API now writes signed credit checkpoints using the dedicated checkpoint key. However, the supported export and offline verifier do not yet carry/check those checkpoints, and a bare NDJSON export cannot prove its tail was not removed. Off-host truncation protection is not yet claimable; it requires checkpoint export/verification and an operator-kept checkpoint (ADR-005 §§5, 13).
- **Governed model state in memory mode.** Without Postgres (development), model state lives in memory and the YAML decides again at restart.
- **Pack/model binding.** A model written for one pack can run under another; it is reported (`model_pack_mismatch`, metric, console banner, approver warning) but not blocked (ADR-010 §4).
- **Downgrade protection at first baseline.** There is no prior version to compare against.
- **Replica convergence.** A one-second background watcher and HTTP/gRPC evaluations plus pack/model catalog, change-request, retention, batch-job, incident, audit, and decision-event routes compare the stored runtime pointer and validate/reload a newer pointer's pinned assets before serving; a read failure, backward version, or invalid asset returns 503. `/v1/runtime` reports `pointer_drift`. Agent evidence/revocation and agent-only audit reads remain on the independent data plane. Review of other operator routes remains part of the approved HA reference plan.
- **Shadow sync when evidence *and* the incident both fail.** The caller still receives `PASS` (shadow must not disrupt the lender's flow); the failure is visible only through `kavach_incident_write_failures_total` and an `ALERT` log line. Monitor that metric.
- **mTLS without `--mtls-principal-san`.** The certificate then only restricts who can connect; the principal comes from a token.
- **Client-certificate revocation.** No CRL or OCSP checking; a certificate stays usable until it expires or its CA is removed (restart needed). Issue short-lived certificates.
- **Binding a token to the certificate that presented it** (RFC 8705). A token presented over mTLS wins over the certificate principal and is not tied to that certificate.
- **Token revocation before expiry.** Access tokens are verified locally and stay valid until `exp` (plus leeway); keep token lifetimes short at the IdP. Certificate-bound tokens (RFC 8705) are P1.
- **HMAC on routes other than `/v1/evaluate`, and on gRPC.** HMAC v2 protects only the evaluate ingestion path; other routes rely on tokens (ADR-008 §3). Database-backed instances now share `/v1/evaluate` nonce reservations; memory-backed development caches remain process-local.
- **Pack integrity at startup in memory mode.** Without Postgres (memory evidence store, development) there is no pointer row; without `--pack-sha256` a restart loads whatever bytes are at `--pack`.
- **First-start baseline.** In a new database, the first API start records its `--pack` as the governed baseline without a change request (audited as `startup_baseline_recorded`); verify it before enabling enforce mode.
- **Pack integrity during evaluation.** Evaluation uses the compiled pack held in memory and does not re-read or re-hash the file.
- **Pack authenticity without signers.** Signature checks apply only when `--pack-signers` is configured; without it, a digest proves "same bytes as last measured", not "approved by a trusted signer".
- **Signing-key protection for keys left in files.** Key files are owner-only (`kavach-keys`) but not encrypted at rest; keep them off the API host. Keys listed in `--hsm-keys` live in an HSM instead (see the guarantee above). The export key can be in an HSM too (`kavach-evidence export --hsm-module`, always generated in the HSM).
- **Signer revocation.** Removing a key from the signers file stops future loads; packs already running stay loaded until the next reload or restart.
- **Pack bytes on the evidence chain.** Evidence identifies packs by `pack_id` and `pack_version`, not by digest; the new agent record type carries the digest (ADR-005).
- **Integrity of the runtime pointer row.** Anyone with write access to Postgres can change pointer paths and digests; governance events on the evidence chain are planned (ADR-005).
- **Legal or regulatory compliance.** Packs are controls *mapped to* regulations and are labelled guidance; they are not legal advice or a compliance certification.
- **v1 evidence signatures.** Existing `decision_event` records are hash-chained but not signed; checkpoint signing arrives with ADR-005.
- **Client time inside CEL rules.** Rules can still read `request.decision_time`; pack authors must use the trusted `now` variable for time decisions (available since M1.5a).
- **CEL memory limits.** The CEL interpreter has no allocation limit, and the timeout is checked between rules, so one expensive expression is not interrupted; packs are bounded by load-time limits instead, and `max_alloc_bytes` is advisory.
- **High availability:** the active/passive direction is approved and write fencing is implemented, but the reference deployment and complete failure/recovery matrix remain pending. Do not enable replicas until the approved HA reference plan is verified. **Cloud KMS key protection, air-gapped deployment** — Stage 2. (PKCS#11 HSMs are supported per signing role.)
- **Correctness of data in the customer's systems of record.**
- **Production hardening of the reference implementation.** The MVP demo is a reference implementation, not a security certification.
